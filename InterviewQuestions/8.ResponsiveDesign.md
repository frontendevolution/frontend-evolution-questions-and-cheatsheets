# Interview Question Bank: Responsive Design — Media & Container Queries
**Pillar:** Foundations Done Right · **Category:** HTML & CSS · **Level:** Advanced · **Year context:** 2026

---

## Conceptual

**1. What's the actual difference between a media query and a container query — not "one uses viewport, one uses container," but why that distinction matters architecturally?**
A media query answers "what does the *page* look like," a container query answers "what space does *this component* have." That's the difference between designing screens and designing components. Once you build with containers, a card doesn't need to know if it's in a sidebar, a grid, or a modal — it just responds to its own box, which is what actually makes a component reusable instead of context-dependent.

**2. What is a containment context, and why won't `container-type: inline-size` work without it?**
Setting `container-type` establishes size containment on that element, which means the browser can lay out its children independently of the parent's own size — that's what breaks the layout circularity problem (child can't query a size that depends on the child). If you forget `container-type`, `container-name` alone does nothing; the query silently never matches.

**3. Explain container query units (`cqw`, `cqi`, `cqb`, `cqmin`, `cqmax`) and when you'd reach for them over `%`.**
These units resolve against the nearest queried container's dimensions instead of the viewport or the immediate parent, so `50cqi` means "50% of the container's inline size" even several DOM levels down. You reach for them when percentage-based sizing breaks because the direct parent isn't the element you actually want to scale against — common in deeply nested design-system components.

**4. What's a "container query unit trap" — a case where using them makes things worse, not better?**
If you size *the container itself* using its own container query units, you get a circular dependency the spec explicitly disallows — the browser just ignores it. It typically bites people styling padding or font-size inside the same element that has `container-type` set on it, expecting `cqi` to reflect the container's own box.

**5. What is `container-type: size` versus `inline-size`, and why is `size` rarely what you want?**
`inline-size` contains only the inline axis (width in horizontal writing modes) and lets the block axis size naturally to content — this is what you use 95% of the time. `container-type: size` contains both axes, which means the element loses its natural height and *must* be explicitly sized, or it collapses to zero — a very easy self-inflicted bug.

**6. What are style container queries (`@container style(...)`), and what problem do they solve that size queries can't?**
Style queries let a component respond to a custom property value on its container rather than its dimensions — e.g. `@container style(--theme: dark)`. This solves theming and variant propagation without needing extra classes or data attributes threaded through the DOM, and it's the piece that makes container queries a real alternative to prop-drilled style variants.

**7. Range syntax (`@media (400px <= width <= 800px)`) shipped as the modern standard — why does it matter beyond being shorter to type?**
It removes the `min-`/`max-` prefix ambiguity and reads in the same direction as the math you're already doing, which cuts down on off-by-one boundary bugs where two queries were meant to be mutually exclusive but actually overlap or gap by a pixel. It's a correctness improvement disguised as syntax sugar.

## Applied / Coding

**8. Write a container query setup for a card component that switches from stacked to horizontal layout once it has at least 400px of inline space.**
```css
.card-wrapper {
  container-type: inline-size;
  container-name: card;
}
.card { display: flex; flex-direction: column; }
@container card (min-width: 400px) {
  .card { flex-direction: row; }
}
```
The container name is optional but worth adding once you have nested containers, so you're explicit about which ancestor a query targets.

**9. You have a grid of cards and want each card to be responsive to its own column width, not the viewport. What's wrong with just adding `container-type` to `.card` itself?**
The container has to be an *ancestor* of the elements being styled, not the element carrying the responsive styles — otherwise you hit the circularity problem from Q4. You need a wrapper: `container-type` goes on the grid item / card wrapper, and the internal card content queries that wrapper.

**10. Refactor this viewport-based component so it's viewport-independent using container queries.**
```css
/* before */
.sidebar-widget { font-size: 14px; }
@media (min-width: 1024px) { .sidebar-widget { font-size: 16px; } }
```
```css
/* after */
.widget-wrapper { container-type: inline-size; }
.sidebar-widget { font-size: 14px; }
@container (min-width: 300px) {
  .sidebar-widget { font-size: 16px; }
}
```
Now the same `.sidebar-widget` renders correctly whether it's dropped into a 300px sidebar or a 900px main column — the viewport-based version was only ever "correct" by coincidence.

**11. How do you combine container queries with `clamp()` for typography instead of stepping font sizes at breakpoints?**
```css
.heading {
  font-size: clamp(1.25rem, 4cqi, 2.5rem);
}
```
This scales continuously with the container's inline size between the min and max bounds, so you avoid the "jump" at breakpoint edges entirely — fewer queries, smoother result, and it composes cleanly with a container query for structural changes layered on top.

**12. Show a media query using `prefers-reduced-motion` combined with a container-responsive animation, and explain why both matter.**
```css
@media (prefers-reduced-motion: no-preference) {
  @container card (min-width: 400px) {
    .card { transition: transform 0.2s ease; }
  }
}
```
The container query controls *when the layout justifies* the animated affordance; the media query controls *whether the user wants motion at all*. Nesting them means you never ship "reduced motion" users a transition just because their container happened to be wide.

## Edge Cases

**13. Why can't you container-query an element's own `display` type change (e.g. going from `display: none` to `display: block`) and have it participate correctly on the first paint?**
If the container is `display: none`, it has no size to establish containment against, so any container query inside it can't evaluate until it's actually rendered — this causes a flash/jump the first time it becomes visible, since the browser has to lay out, measure, then re-evaluate. Media queries don't have this problem because viewport size is always known.

**14. What happens when a container query and a media query target the same property with conflicting values, and which wins?**
Ordinary CSS cascade and specificity rules apply — there's no special container-query priority. Whichever rule comes later in source order (given equal specificity) wins, which means mixing the two carelessly produces layout that depends on stylesheet order rather than intent; keep container-based and viewport-based rules for the same property physically grouped so this is visible in code review.

**15. Your container query works in Chrome but the layout "jumps" once on load in Safari before settling. What's likely happening?**
This is usually a containment/paint timing difference — the engine calculates layout before container queries have a stable value to evaluate against, especially with content that affects its own container's intrinsic size (fonts loading, images without dimensions). Reserve space with `aspect-ratio` or explicit dimensions on replaced content so the container size is stable before first paint, rather than depending on content to settle it.

**16. Can you container-query based on aspect ratio, not just width? Give a real use case.**
Yes — `@container (aspect-ratio > 1/1)` or `(orientation: landscape)` are valid container query conditions since containers support both size and orientation. A real case: a video player component that swaps control layout when its container is wider-than-tall versus a portrait embed, independent of the actual viewport orientation.

## Comparison

**17. "Just use container queries everywhere and stop using media queries" — agree or disagree, and why?**
Disagree. Container queries solve component-level responsiveness; media queries are still correct for page-level concerns — overall layout shell, print styles, `prefers-color-scheme`, `prefers-reduced-motion`, and anything that's genuinely about the device/viewport rather than a specific component's available space. The skill isn't picking one, it's knowing which layer a given decision belongs to.

**18. Compare container queries to the older JS-based "resize observer + conditional className" pattern for responsive components. What did teams give up building it that way, and what do they get back now?**
The JS pattern worked but cost a render cycle per resize, needed manual debouncing, and coupled layout logic to component state — meaning designers couldn't touch it without a PR. Container queries move that logic back into CSS: no re-render, no JS bundle cost, and it's declarative enough that non-engineers can reasonably read and adjust it.

**19. Compare `cqi` units to `vw`/`vh` and to `%`. When does each actually make sense?**
`%` resolves against the immediate parent and breaks the moment you nest a few levels deep with mixed box models; `vw`/`vh` resolve against the viewport and ignore layout entirely, which is why 100vw famously overflows past scrollbars; `cqi`/`cqb` resolve against a deliberately declared container, giving you predictability without viewport coupling. If you're reaching for `vw` inside a component that isn't meant to be viewport-aware, that's usually a sign it should be `cqi` instead.

## React / Next.js in Practice

**20. You're building a design-system `<Card>` component in a Next.js app meant to be dropped into a sidebar, a modal, and a full-width section. Why is this the textbook case for container queries over Tailwind's default responsive variants?**
Tailwind's default `sm:`/`md:` variants are viewport breakpoints, so the same `<Card>` renders identically whether it's in a 280px sidebar or a 1200px hero section — that's the bug container queries exist to kill. You'd wrap the card's parent in `@container` (Tailwind v4's `@container` / `@sm:` container variants ship natively now) so the exact same component genuinely adapts per-instance without prop-drilling a `variant="compact"` flag through every call site.

**21. In a Next.js app using CSS Modules or Tailwind, where does `container-type` typically need to go relative to your component boundary, and what's the common mistake?**
It has to go on a wrapper *outside* the component that needs to respond — not on the component's own root class — because of the circularity issue. The common mistake in React specifically is setting `container-type` directly on the component you're also styling with container queries, which works by accident in simple cases and then silently fails once that component gains a child that also needs the containment context.

**22. How does streaming SSR / React Server Components interact with container queries in terms of layout shift?**
Because container queries need actual box dimensions to evaluate, and RSC/streaming can deliver chunks of a page at different times, a container-queried component can flash its "collapsed" state before its real container width is known — same root cause as Q13, but now distributed across server-streamed boundaries instead of just client rendering. Reserve intrinsic size (skeletons with real dimensions, not zero-height placeholders) for anything container-queried inside a Suspense boundary.

**23. A teammate's PR adds `container-type: inline-size` to a shared layout primitive (like your app's `<Stack>` or `<Box>`) used in hundreds of places. What do you flag in review?**
Adding containment to a widely-reused primitive changes layout behavior for every consumer at once — size containment can affect how that box's content influences intrinsic sizing up the tree, which can silently break `min-content` dependent layouts elsewhere. Flag it for a scoped wrapper instead of touching the shared primitive, and ask for a visual diff/regression check across the app, not just the one screen the PR was written for.

## AI-Era Angle

**24. An AI assistant generates a component with `container-type: inline-size` but no `container-name`, and three nested child components all have `@container` rules. What's the actual risk, and why does it "work" in the demo but break later?**
Without names, every `@container` query resolves against the *nearest* ancestor with containment set — which is fine until someone (or the AI, in a later prompt) adds another container-typed wrapper in between. The demo works because there's only one containment ancestor in scope at the time; it silently starts targeting the wrong container the moment the DOM structure changes, and there's no error, just wrong layout. This is exactly the kind of bug that passes a quick visual check and ships.

**25. You ask an AI coding assistant to "make this card responsive." It comes back with a `@media` query only. Why does this happen, and what should you actually be prompting for?**
Media queries dominate the training data by volume and are the "safe default" pattern, so unless you specify component-level responsiveness explicitly, most assistants reach for viewport breakpoints even in 2026 codebases where container queries are the better fit. Prompt for the actual constraint — "this card is reused in a sidebar and a full-width grid, make it respond to its own available width" — because the assistant can't infer reuse context from a single file it's looking at.

**26. AI-generated CSS often sets `container-type: size` where `inline-size` was actually needed. Why does this mistake happen, and how do you catch it in review without running the app?**
`size` reads as the more "complete" or "safe" option to a model pattern-matching on the word "container," but it forces both axes into containment, which strips natural height unless every dimension is explicitly set — a mistake that's invisible in the diff and only shows up as collapsed content at runtime. In review, treat any `container-type: size` as a flag needing justification; if there's no explicit height math nearby, it's very likely meant to be `inline-size`.

**27. You're reviewing an AI-generated PR that mixes Tailwind's viewport breakpoints and container query variants on the same element for what looks like the same visual goal. How do you evaluate whether this is intentional or a copy-paste artifact from mismatched training examples?**
Check whether the element actually sits inside a `@container`-established ancestor at all — AI assistants frequently emit `@sm:` container variants as if they're interchangeable with `sm:` viewport variants because they look nearly identical in class-name form, and if there's no containing context, the container variant is dead code that never applies. This is a case where you genuinely need to trace the DOM tree yourself; the naming similarity is precisely what makes it easy for a model (and a fast human reviewer) to miss.

**28. Beyond writing correct syntax, why does understanding container vs. media queries stay a "must-know" skill in an AI-assisted workflow rather than something you can fully delegate?**
Because the *decision* of which responsiveness model a given component needs is a design judgment about ownership and reuse boundaries — something the AI can't determine from syntax alone, only from context you have to supply and verify. An assistant will happily generate confident, working-looking CSS for the wrong model entirely (viewport-based responsiveness for a genuinely reusable component), and catching that requires knowing what correct actually looks like, not just what compiles without errors.
