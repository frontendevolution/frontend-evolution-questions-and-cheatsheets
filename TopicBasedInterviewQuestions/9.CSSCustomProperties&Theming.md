# CSS Custom Properties & Theming — Interview Question Bank

**Pillar:** Foundations Done Right · **Category:** HTML & CSS · **Level:** Advanced

---

## Conceptual

**1. What actually makes a custom property different from a Sass/LESS variable?**
Sass variables are compile-time — they get inlined into static values before the browser ever sees them. Custom properties live in the cascade at runtime: they inherit, they can be overridden per element, they respond to media queries and JS without a rebuild. If you're still explaining this as "CSS variables but worse," you're missing the actual feature — runtime reactivity.

**2. Walk through how inheritance works for a custom property vs a regular CSS property.**
Custom properties inherit by default from parent to child unless explicitly registered otherwise via `@property` with `inherits: false`. That means redefining `--accent` on a wrapper cascades down to every descendant that references `var(--accent)`, even ones with no idea the override happened. This is the exact mechanism theming relies on, and the exact mechanism that causes "why is this random button suddenly blue" bugs.

**3. What problem does `@property` actually solve that plain `--x` doesn't?**
Unregistered custom properties are untyped strings — the browser can't interpolate them, so you can't animate a gradient angle or a color stop smoothly. `@property` gives you a syntax type, an initial value, and inheritance behavior, which unlocks smooth transitions/animations and guards against invalid values silently breaking your cascade. It's the difference between "text substitution" and "an actual typed CSS value."

**4. Explain the fallback syntax in `var(--x, fallback)` — when does the fallback actually kick in?**
The fallback resolves only when `--x` is unset or invalid at compute time for that element — not when it's merely empty in a parent scope. A common misconception is that an empty string value triggers the fallback; it doesn't, an explicitly set empty value is still "set." Know this before you debug a theme that "isn't falling back" as expected.

**5. How do cascade layers (`@layer`) interact with custom property theming?**
Layers control which _rule_ wins, not which custom property value resolves — custom properties still follow normal specificity and source order within resolution, but layering lets you define a base theme layer and safely override it in a later layer without specificity wars. For design systems, this replaces the old `!important` and over-specific selector hacks people used to force theme overrides.

**6. Do custom properties pierce the Shadow DOM boundary?**
Yes — inherited custom properties cross into shadow trees since they follow the same inheritance mechanism as `color` or `font-size`; this is the sanctioned way to theme web components from the outside. Everything else about the shadow boundary is encapsulated, but custom properties were deliberately designed as the styling API surface for components.

**7. What's the real difference between reading a custom property with `getComputedStyle` vs `element.style.getPropertyValue`?**
`getComputedStyle(el).getPropertyValue('--x')` resolves the cascade — inherited, layered, media-queried — and gives you the actual used value. `element.style.getPropertyValue('--x')` only reads the inline style, so it returns empty if the value came from a class or inherited context. Mixing these up is a classic "why is my JS theme sync reading blank" bug.

## Applied / Coding

**8. Write a light/dark theme system using `light-dark()` instead of duplicating custom property blocks.**

```css
:root {
  color-scheme: light dark;
  --bg: light-dark(#fff, #0b0b0c);
  --fg: light-dark(#111, #e8e8e8);
}
body {
  background: var(--bg);
  color: var(--fg);
}
```

`light-dark()` collapses what used to be two full `:root` blocks gated behind `prefers-color-scheme` or a `.dark` class into one declaration, as long as `color-scheme` is set. You still need a class or `color-scheme` override for manual toggle support, but the token duplication disappears.

**9. A teammate sets `el.style.setProperty('--x', newValue)` in JS but the visual doesn't update. What are you checking?**
First, whether `--x` is actually consumed via `var(--x)` anywhere in the applicable rule for that element — setting an unused custom property does nothing visually. Second, whether a more specific rule or later layer redefines `--x` closer to the element, shadowing the inline value. Third, if it's a registered `@property` with a syntax type, whether `newValue` is actually valid for that type — invalid values are dropped, not coerced.

**10. Register an animatable custom property for a spinner's rotation and explain why it needs `@property`.**

```css
@property --angle {
  syntax: "<angle>";
  inherits: false;
  initial-value: 0deg;
}
.spinner {
  animation: spin 1s linear infinite;
}
@keyframes spin {
  to {
    --angle: 360deg;
  }
}
```

Without registration, `--angle` is an opaque string and the browser can't compute intermediate frames, so animating it does nothing. Typing it as `<angle>` tells the engine how to interpolate, which is what actually makes the keyframe work.

**11. Design a component-scoped theming API for a design system button using custom properties as the public contract.**
Expose only a curated set of `--button-*` custom properties (`--button-bg`, `--button-fg`, `--button-radius`) as the component's styling API, with internal styles consuming them and falling back to design tokens. This gives consumers an explicit override surface without leaking full CSS access to component internals — the property names _are_ the API, so treat renaming one as a breaking change.

**12. Set up a fallback chain for multi-brand white-label theming where a brand can override some tokens but not others.**

```css
:root {
  --brand-primary: var(--tenant-primary, #2563eb);
  --brand-radius: var(--tenant-radius, 8px);
}
```

Each tenant only needs to define the `--tenant-*` overrides they care about; everything else silently falls through to the shared default. The gotcha is fallback chains only go one level deep in evaluation per `var()` call, so deeply nested fallback chains need to be flattened, not stacked recursively.

## Edge Cases

**13. A custom property is defined with an invalid value for its registered type. What happens, and why does this surprise people?**
The property resolves to its `initial-value` for that element (guaranteed-invalid-at-computed-value-time behavior for registered properties), not to the last valid inherited value — this trips people up because they expect it to "fall back up the tree." Unregistered custom properties behave differently: invalid usage there only breaks at the point the `var()` is substituted into an actual property, and _that_ property falls back to its own inherited/initial value.

**14. Why doesn't a custom property set on `::before` show up when read from the parent element in JS?**
Pseudo-elements are separate boxes in the render tree with their own computed style; a custom property set inside `.card::before { --x: red }` exists only on that pseudo-element's computed style, it doesn't propagate back up to `.card`. Inheritance flows down the tree, never up — a surprisingly common misconception once pseudo-elements enter the picture.

**15. How do custom properties interact with container queries when a component's theme should change based on its container size, not the viewport?**
You can redefine custom properties inside a `@container` block scoped to a container context, letting a card component swap `--gap` or `--font-size` tokens based on its own container's width rather than global breakpoints. This is what makes container-query-driven design systems actually composable — the same component can self-theme differently in a sidebar vs a main content area.

## Comparison

**16. In 2026, when do you reach for custom properties vs Tailwind's theme tokens vs CSS-in-JS?**
Custom properties are the runtime layer now regardless of stack — even Tailwind v4's theme system compiles down to CSS custom properties under the hood, and most CSS-in-JS libraries lost ground precisely because runtime style injection couldn't compete with zero-runtime custom-property theming plus static extraction. The real decision isn't "custom properties vs the alternative" anymore, it's how you author and scope them — utility classes, CSS Modules, or hand-rolled tokens.

**17. Sass variables vs custom properties — is there still a reason to reach for Sass variables in 2026?**
Sass variables still make sense for build-time constants that never change at runtime — breakpoint values used only in `@media` conditions, or values consumed by a build tool rather than the browser. Anything that needs to respond to theme switching, user preference, or per-instance overrides belongs in a custom property; conflating the two is how teams end up with theme values baked into a JS bundle that can't be overridden without a rebuild.

## System Design

**18. Design a theming system for a multi-tenant SaaS product with white-labeling, dark mode, and per-user density preferences, rendered with Next.js SSR.**
Structure tokens in three layers: base design tokens (`--space-*`, `--radius-*`), semantic tokens that reference base tokens (`--surface-bg: var(--gray-50)`), and tenant/user overrides injected as a `<style>` block or `data-*` attribute resolved server-side from tenant config, so first paint is already correctly themed with no flash. Dark mode and density become attribute-driven overrides (`data-theme`, `data-density`) scoped at the root, read server-side from a cookie so SSR output matches client expectations on hydration — the key architectural decision is keeping override resolution server-side, not client-side after mount.

## React & Next.js in Practice

**19. Users report a flash of the wrong theme on page load in a Next.js app using custom properties for dark mode. What's the root cause and fix?**
The theme preference typically lives in `localStorage`, which isn't available during SSR, so the server renders a default theme and the client repaints after hydration reads the stored value — classic FOUC. Fix it by reading the preference from a cookie (available server-side) instead of `localStorage`, and setting the `data-theme` attribute during SSR so the first HTML response is already correct.

**20. Where in a Next.js App Router tree can you actually set root-level custom properties, given Server vs Client Component boundaries?**
Root custom properties like `--brand-primary` are just CSS — they can be set in a Server Component's rendered markup (inline style or class on `<html>`/`<body>` in `layout.tsx`) without needing "use client," since it's static output, not interactivity. Reserve Client Components only for the _reactive_ part — the toggle that mutates the attribute after a click — not for the initial value itself; over-clienting the whole theme provider is a common unnecessary bundle-size mistake.

**21. How do custom properties interact with CSS Modules scoping in a Next.js project?**
CSS Modules hash class names but do _not_ scope custom property names — `--gap` defined in one Module file is still globally visible in the cascade because custom properties aren't subject to the module's local scoping transform. This means two different Modules can silently clash on the same `--gap` name; the convention that saves you is prefixing tokens per component (`--card-gap`) rather than relying on Module isolation to protect you.

**22. A teammate writes `<div style={{ '--accent': accentColor }}>` in TypeScript and it fails to compile. Why, and what's the fix?**
React's `CSSProperties` type doesn't natively include arbitrary custom property keys, so TypeScript rejects the object literal. The fix is casting the style object as `React.CSSProperties & Record<'--accent', string>`, or more commonly using a shared `CSSVars` helper type across the codebase — worth knowing because AI assistants frequently paper over this with a blanket `as any`, which silently swallows real typos in property names later.

## AI-Era Review Questions

**23. An AI assistant generates a component where every instance redefines the same six custom properties inline instead of inheriting from a shared theme scope. Why is this wrong, and how would you flag it in review?**
This defeats the entire point of the cascade — each component becomes an isolated island that can't be re-themed globally, which is exactly the copy-paste problem custom properties exist to solve. In review, the fix isn't "delete the duplication," it's asking _why_ the AI reached for inline redefinition — usually because it wasn't given the actual token scope/hierarchy in context, so the real fix is prompting with the design token structure, not just asking it to "clean up the CSS."

**24. AI-generated code implements a theme toggle by reading `localStorage` in a `useEffect` and setting the custom property on mount in a Next.js app. What breaks, and why does the AI not catch it?**
This reintroduces the exact FOUC/hydration-flash problem discussed above — the server has no access to `localStorage`, so it SSRs a default theme, then the client flips it post-mount, causing a visible flash and a hydration mismatch warning if the theme also affects markup. AI tools default to this pattern because it's the most common StackOverflow-era answer in their training distribution, not because it's correct for SSR frameworks — you have to know to redirect it toward cookie-based server reads.

**25. AI generates `--spacing: 16;` and uses it as `padding: var(--spacing);`. What's actually wrong here, and would it visibly fail?**
Unregistered custom properties store raw token text with no unit coercion — `var(--spacing)` substitutes literally to `padding: 16;`, which is invalid CSS (no unit) and gets dropped, falling back to `padding`'s initial value, silently. It won't throw an error anywhere, it'll just look "slightly off" in the browser, which makes it a genuinely dangerous class of AI-generated bug — no lint error, no console warning, just wrong spacing that's easy to miss in a fast review pass.

**26. AI-generated code uses `@property` to register a custom property but you notice it forgot `inherits`. Why does this matter enough to block the PR?**
`inherits` isn't optional metadata — omitting it doesn't give you a sane default, it's a required descriptor, and if AI-generated code leaves it out the `@property` rule is invalid and the browser ignores the whole registration, silently falling back to unregistered (untyped, uninterpolatable) behavior. This is a good example of why "the code runs and looks fine locally" isn't sufficient review for AI output involving typed CSS — you need to actually know the `@property` spec surface to catch a _missing_ declaration, not just a wrong one.

**27. Why won't AI coding assistants make deep custom-property theming knowledge obsolete, even as they get better at writing the syntax?**
AI can generate syntactically valid `@property` rules, fallback chains, and `light-dark()` calls all day — what it consistently gets wrong is the _architecture_ decision of where a token boundary should live in your specific app (tenant-level vs component-level vs page-level) and the _cascade reasoning_ needed to debug why an override isn't winning. Both of those require understanding inheritance, specificity, and layer order well enough to read generated CSS and predict its actual runtime behavior — that's a mental model, not a syntax pattern, and it's exactly what separates "code that compiles" from "code that's correct in production."
