# CSS Grid — Internal Teaching Doc
**Pillar:** Foundations Done Right | **Category:** HTML & CSS | **Level:** Advanced

## Core Concept

CSS Grid is a two-dimensional layout system — it controls rows AND columns simultaneously, unlike Flexbox which is fundamentally one-dimensional (even when it wraps). The mental model shift that separates intermediate devs from advanced ones: Grid isn't "a layout you apply to children," it's a coordinate system you define on the parent, and children opt into placement within that system. You're not stacking boxes — you're placing items onto a grid that exists independently of content.

The core insight most devs miss: **the grid exists whether or not you explicitly place items on it.** Implicit tracks, auto-placement algorithms, and the difference between explicit and implicit grids are where real fluency lives.

## Full Mechanics

**Establishing a grid container:**
```css
.container {
  display: grid; /* or inline-grid */
}
```

**Defining explicit tracks:**
```css
.container {
  grid-template-columns: 1fr 2fr 1fr;
  grid-template-rows: repeat(3, minmax(100px, auto));
}
```

- `fr` is a fraction unit of *remaining space after fixed-size tracks and gaps are subtracted* — not a percentage of the container. This trips people up constantly.
- `repeat()` supports `auto-fill` and `auto-fit` — critical for responsive grids without media queries:
```css
grid-template-columns: repeat(auto-fit, minmax(220px, 1fr));
```
`auto-fill` keeps empty tracks (useful when track count should stay stable); `auto-fit` collapses empty tracks to zero width, letting existing items stretch. This distinction is a favorite senior-interview trap.

**Implicit grid:** items placed outside the explicit definition generate implicit tracks, sized via `grid-auto-rows` / `grid-auto-columns` (default: `auto`). `grid-auto-flow: row | column | dense` controls how auto-placed items fill gaps — `dense` backfills holes but can visually reorder DOM content, a subtle a11y hazard since visual order and DOM/tab order diverge.

**Placement:**
```css
.item {
  grid-column: 2 / 4;      /* start line 2, end line 4 */
  grid-row: span 2;         /* span 2 tracks from auto-placed start */
  grid-area: header;        /* named area shorthand */
}
```
Grid lines are 1-indexed and count both positive (left/top-to-right/bottom) and negative (from the end). `grid-column: 1 / -1` = full width, a pattern worth memorizing.

**Named template areas** — the most readable syntax for complex layouts:
```css
.container {
  grid-template-areas:
    "header header"
    "sidebar content"
    "footer footer";
  grid-template-columns: 250px 1fr;
}
.header { grid-area: header; }
```

**Alignment:** `justify-items`/`align-items` (items within their cells), `justify-content`/`align-content` (the whole grid within the container when tracks don't fill it), and `place-items`/`place-content` shorthands. Per-item overrides: `justify-self`/`align-self`.

**Gaps:** `gap`, `row-gap`, `column-gap` — no more margin-hack spacing between grid items.

**2026-current additions worth knowing:**
- **Subgrid** (`grid-template-columns: subgrid`) — now broadly supported across evergreen browsers. Lets nested grids inherit parent track sizing, solving the long-standing "align nested card content across a grid" problem without duplicating track definitions. This is the single biggest Grid-related shift in the last two years and most devs still don't use it.
- **`masonry` value for `grid-template-rows`** — still experimental/behind flags in most engines as of 2026; don't teach it as production-ready, but flag it as "coming."
- Grid + container queries (`container-type: inline-size`) are now the standard combo for component-level responsiveness, replacing viewport-based media queries for anything living inside a reusable component.

## Common Misconceptions

- "Grid replaces Flexbox" — false. Grid = 2D layout of a container; Flexbox = 1D distribution/alignment, often nested *inside* grid cells. Advanced devs combine them constantly.
- "`fr` units are percentages" — they're not; they don't account for content minimums unless you also manage `minmax()` and default `min-width: auto` behavior on grid items (a very common overflow bug source).
- "Auto-placement is unpredictable" — it's deterministic; devs just haven't internalized the algorithm (row-first by default, respects spans, backfills only with `dense`).
- Believing you need explicit row/column counts everywhere — implicit grids with `auto-fit`/`minmax` remove 80% of manual breakpoint work.

## Current Best Practices (2026) vs Outdated

| Outdated | Current |
|---|---|
| Float/table-based layout grids | Grid + subgrid |
| Media-query-driven responsive columns | `auto-fit`/`minmax` intrinsic responsiveness |
| Duplicated track definitions for nested alignment | `subgrid` |
| JS-calculated masonry libraries for simple cases | CSS Grid + `auto-flow: dense` (true masonry still needs JS or the experimental value) |
| Viewport media queries inside reusable components | Container queries paired with grid |

## Why It Matters at a Senior Level

Grid separates devs who can build layout from devs who understand layout *systems*. Senior-level signal: knowing when Grid is the wrong tool (simple 1D toolbars → Flexbox), diagnosing overflow caused by implicit `min-width: auto`, and architecting component libraries where subgrid keeps design-system alignment consistent without prop-drilling pixel values. It's also a common whiteboard/live-coding topic precisely because it reveals whether someone has memorized syntax or actually understands the placement algorithm.

## Relevance in React/Next.js Projects

- **Dynamic column counts from data:** a common pattern is generating `gridTemplateColumns` inline based on array length or CMS-driven layout config — `style={{ gridTemplateColumns: `repeat(${cols}, 1fr)` }}`. Know when this is legitimate (data-driven layouts) vs when it should just be `auto-fit`/`minmax` in a CSS Module to avoid unnecessary re-renders on resize.
- **Design systems and subgrid:** component libraries (cards, table-like list rows) built with Grid inside a parent Grid — subgrid is now the correct way to keep child components' internal columns aligned to the parent's tracks without every consumer redefining track sizes. This is a strong "I know 2026 CSS" signal in code review.
- **Server Components + CSS Modules/Tailwind arbitrary values:** Tailwind's `grid-cols-[...]` arbitrary value syntax is common for one-off grids; devs need to know when to reach for a utility class vs a dedicated CSS Module for maintainability — a real architectural decision, not just style preference.
- **Layout shift and Core Web Vitals:** Next.js apps rendering grids with images/cards need explicit `grid-auto-rows` or aspect-ratio boxes to prevent CLS during hydration, especially with streaming/Suspense boundaries where content pops in asynchronously.
- **RTL/i18n:** logical properties (`grid-column: 1 / -1` behaves fine, but `justify-items: start` respects writing direction) matter more in Next.js apps shipping multiple locales — using physical left/right assumptions breaks RTL layouts.

## Relevance in the AI Era

- AI assistants frequently generate grids with hardcoded `grid-template-columns: 1fr 1fr 1fr` instead of `repeat(auto-fit, minmax(...))`, producing layouts that break at arbitrary viewport widths. They optimize for "looks right in the prompt's example," not intrinsic responsiveness — devs must recognize and refactor this.
- Copilot/Cursor commonly overuse `grid-column: span N` without setting a sensible implicit row sizing strategy, causing content to silently overflow or collapse when item count doesn't divide evenly — this passes visual smoke-tests but breaks with real dynamic data.
- AI tools rarely reach for subgrid even when it's the objectively correct solution, because it's a comparatively newer, less-represented pattern in training data — devs need to know it exists and *prompt for it explicitly* or manually refactor nested-grid alignment hacks the AI defaults to instead.
- Generated code often ignores the `min-width: auto` overflow gotcha entirely, producing grids that look fine until a child has an unbreakable long string (URL, filename) — this is a classic "code reviews fine, breaks in production" AI output pattern.
- Why this doesn't get automated away: Grid bugs are almost always *layout algorithm* bugs, not syntax bugs — the code is syntactically valid CSS that produces the wrong visual result under specific content/viewport conditions. Catching that requires understanding the placement algorithm, not reading the CSS. AI can produce valid Grid syntax fluently; it can't reliably reason about how that syntax behaves across the full space of dynamic content lengths, item counts, and viewport widths a real product will hit — that judgment is still on the human reviewer.
