# Foundations Done Right — Forms, Input Types, Label, Select, Textarea, Attributes & Validation

## Core Concept

A form is not "a div with some inputs in it." It's a native browser contract: the `<form>` element, its controls, and the browser's built-in validation/submission engine all cooperate to collect, validate, and transmit structured data — with zero JavaScript required for the basic case. Most devs never learn this baseline because React abstracts it away on day one. That's exactly why it's worth teaching: the abstraction leaks constantly, and the leaks show up as accessibility bugs, autofill failures, and "why is my form submitting twice" incidents.

The mental model to teach: **the browser already built a form engine.** Every framework form library (React Hook Form, Formik, Conform) is a layer on top of that engine, not a replacement for it. If you don't know the engine, you can't debug the layer.

## Full Mechanics

### The `<form>` element
- Wraps controls into one submittable unit.
- Key attributes: `action`, `method` (`get`/`post`), `enctype` (`application/x-www-form-urlencoded`, `multipart/form-data` for files, `text/plain`), `novalidate` (disables built-in validation), `autocomplete`.
- Any button inside a form defaults to `type="submit"` unless specified — this is the #1 cause of "why did my form submit when I clicked a random button" bugs.

### Labels
- `<label for="id">` paired with a matching `id` on the control, OR the control nested inside the label (implicit association).
- A label is not decoration — it expands the click/tap target, and it's the primary accessible name for the control read by screen readers.
- `aria-label` / `aria-labelledby` are fallbacks for when a visible `<label>` isn't feasible, not a substitute for one.
- Placeholder text is **not** a label. It disappears on input, has poor contrast requirements, and isn't reliably announced. "Placeholder as label" is a top misconception among juniors.

### Input types
`type` changes parsing, virtual keyboard, and validation behavior — it is not cosmetic:
- `text`, `email`, `password`, `tel`, `url`, `search`
- `number` (returns a value that's already numeric-shaped; has quirky scroll-wheel and arrow-key increment behavior — often disabled deliberately)
- `date`, `time`, `datetime-local`, `month`, `week`
- `checkbox`, `radio` (radios sharing a `name` form a mutually exclusive group)
- `range`, `color`, `file`
- `hidden` — still submitted, invisible, not a security boundary
- `submit`, `reset`, `button`

Each of these auto-adjusts mobile keyboards (`email` gives an `@` key, `tel` gives a numpad) and gives free validation (`email`/`url` check basic shape). Using `type="text"` for everything throws away this for free.

### Select and options
- `<select>` with `<option>` children; `multiple` attribute turns it into a multi-select list box.
- `<optgroup label="...">` groups related options.
- Controlled default via `selected` attribute on an `<option>`, not via JS-only state in native HTML.

### Textarea
- `<textarea>` is not a self-closing tag — its content is the initial value, not a `value` attribute (this matters a lot once you hit React, see below).
- `rows`/`cols` set intrinsic size; `resize` is a CSS property (`none`, `vertical`, `horizontal`, `both`).

### Universal and validation attributes
- `name` — required for the value to be submitted at all. No `name`, no data.
- `required`, `disabled`, `readonly` (readonly still submits; disabled does not).
- `minlength`/`maxlength`, `min`/`max`/`step` (numeric/date types), `pattern` (regex string, anchored implicitly).
- `autocomplete` — should use the standardized token list (`autocomplete="email"`, `"new-password"`, `"street-address"`, `"cc-number"`, etc.), not just `"on"`/`"off"`. This is what enables password managers and autofill to work correctly — a huge, underrated UX and security lever.
- `autofocus`, `multiple` (email, file), `list` (pairs with `<datalist>` for suggestions).

### Native constraint validation API
- Browser validates automatically on submit unless `novalidate` is set.
- CSS pseudo-classes `:invalid`, `:valid`, `:required`, `:optional`, `:in-range`, `:out-of-range`, `:user-invalid` (newer, avoids showing red before the user has interacted).
- JS API: `element.checkValidity()`, `element.reportValidity()`, `element.setCustomValidity("message")`, and the `ValidityState` object (`valueMissing`, `typeMismatch`, `patternMismatch`, `tooShort`, `rangeOverflow`, etc.).

## Common Misconceptions
- "Placeholder is fine as a label" — it's not, for accessibility and UX reasons.
- "`required` alone is enough validation" — client-side validation is a UX convenience only; it's trivially bypassed, so server-side/API validation is always mandatory.
- "`disabled` inputs still submit their value" — they don't. Use `readonly` if you need the value to persist in the payload.
- "Radio buttons need unique `name`s" — the opposite: they need the **same** `name` to behave as a group.
- "Number inputs give you a reliable number" — they can still return an empty string, and locale/step quirks make them less reliable than they look; many production forms deliberately use `type="text" inputmode="numeric" pattern="[0-9]*"` instead.

## 2026 Best Practices vs Outdated Approaches
- Use semantic input types and native validation attributes as the first line of defense — don't hand-roll regex validation for things like email format that the browser already does.
- Use `:user-invalid` / JS-tracked "touched" state instead of showing errors on first render (old pattern: `:invalid` styling firing before any interaction, which reads as broken UI).
- Use the standardized `autocomplete` token vocabulary — this is a current accessibility and security expectation, not optional polish.
- Prefer native `<dialog>`/`popover` + form association patterns for things like confirm-before-submit flows over custom modal-and-JS reimplementations.
- Outdated: relying purely on JS-triggered validation on every keystroke with no debouncing, and building fully custom `<select>` replacements from `<div>`s without ARIA `combobox` semantics — both create accessibility regressions that current tooling flags immediately (axe, Lighthouse, eslint-plugin-jsx-a11y).

## Why It Matters at a Senior Level
Junior devs treat forms as UI. Senior devs treat forms as a data contract with security, accessibility, and business-logic implications: what's submitted, what's validated where, what happens on JS failure, and what a screen reader user or password manager experiences. Interviewers in 2026 routinely probe this — not "build a form" but "why did this label/input pairing break assistive tech" or "why is this select inaccessible" — because it exposes whether a candidate actually understands the platform or has only ever used a form library.

## Relevance in React/Next.js Projects

- **Controlled vs uncontrolled inputs**: React's `value`/`onChange` controlled pattern fights the native DOM model. Forgetting `defaultValue` vs `value` causes the classic "controlled input became uncontrolled" console warning — a rite of passage bug.
- **`<textarea>` in JSX**: because textarea content isn't an attribute in JSX either — you must use `value`/`defaultValue`, not children, unlike raw HTML. This trips up devs who "know HTML" but not JSX's model of it.
- **Server Actions and native forms are back in style**: Next.js App Router encourages `<form action={serverAction}>` using the native form submission model with progressive enhancement, rather than only `onSubmit` + `preventDefault()` + fetch. This is a real architectural shift worth calling out — forms-as-native-mechanism is trendy again, not legacy.
- **`useFormStatus` and `useActionState`** (React 19) hook into native form submission state (pending, errors) without manual state wiring — understanding native form semantics is a prerequisite to using these correctly.
- **Hydration mismatches**: uncontrolled inputs with server-rendered `defaultValue` that differs from client state cause hydration warnings — another place where "just an HTML form" knowledge saves debugging time.
- **Form libraries** (React Hook Form, Conform, Zod-based schema validation) are layered on top of the native constraint validation API — reading their source or debugging their edge cases requires knowing `ValidityState` and `checkValidity()` cold.
- **Accessibility in component libraries**: custom `<Select>`/`<Combobox>` components (Radix, shadcn/ui) reimplement `<select>` semantics with ARIA — you need to know what native `<select>` guarantees for free to judge whether the custom version is actually equivalent.

## Relevance in the AI Era

- AI assistants reliably generate forms that "look right" but skip `<label for>` pairing, using placeholder-only or unlabeled inputs — because visually it renders fine and the model isn't rendering a screen reader in its head. This is the single most common AI-generated forms defect worth calling out in content.
- AI tools frequently default to `type="text"` for everything (email, phone, numbers) instead of semantic types, losing free validation and correct mobile keyboards — because generic `text` "works" in every case the model tests against.
- AI-generated React forms often mix controlled and uncontrolled patterns inconsistently across the same form (some inputs get `value`+`onChange`, others get `defaultValue`, arbitrarily) — a dev must manually audit for this since it silently produces buggy, half-controlled forms.
- AI assistants tend to under-use native validation attributes (`required`, `pattern`, `minlength`, `autocomplete` tokens) in favor of writing custom JS validation logic from scratch — technically functional, but reinventing what the platform already provides for free, and often missing edge cases the native API handles automatically.
- Agentic tools asked to "add validation" will often add only client-side checks and skip server-side/API validation entirely unless explicitly prompted — a reviewer must know that client-side validation is never sufficient and check the server boundary independently.
- Bottom line for content: AI can generate the JSX for a form in seconds, but it cannot be trusted to get labels, semantic input types, autocomplete tokens, or the controlled/uncontrolled boundary right by default — reviewing AI-generated forms requires the exact platform knowledge this doc covers, not less of it.
