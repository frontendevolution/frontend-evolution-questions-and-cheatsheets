# CSS Units (px, rem, em, vw, %)

**Pillar:** Foundations Done Right | **Category:** HTML & CSS | **Level:** Beginner

## Core Concept

CSS units aren't interchangeable stylistic choices — each one answers a different question:

- **px** — "this many physical-ish pixels, fixed, no relationship to anything else"
- **em** — "relative to the font-size of *this element's parent* (for font-size) or *this element itself* (for everything else, like padding/margin)"
- **rem** — "relative to the font-size of the **root** (`html`) element, always, no matter how deep you're nested"
- **%** — "relative to the parent's corresponding property" (width % → parent width, but height % is notoriously conditional — see below)
- **vw / vh** — "relative to 1% of the viewport's width/height"

The senior-level insight most devs never get explicitly taught: **units aren't about size, they're about what you want the value to *track*.** Every time you pick a unit, you're deciding "if X changes, should this value change too?" — X being the parent's font-size, the root's font-size, the viewport, or nothing at all.

## Full Mechanics

### px
Absolute (technically a "reference pixel," not a literal screen pixel — it's normalized across devices via CSS's pixel-density math). It does not respond to the user's browser font-size setting. If a user bumps their default font size for accessibility, `font-size: 16px` stays 16px. This is the core reason `px` is discouraged for typography.

### em
```css
.card { font-size: 20px; }
.card p { font-size: 1.2em; } /* 24px — 1.2 × parent's 20px */
.card p { padding: 1em; }     /* 24px — 1em uses THIS element's own resolved font-size */
```
`em` compounds. Nest three levels of `1.2em` font-sizes and you get multiplicative growth (20 → 24 → 28.8 → 34.56), which is the classic "why is my text huge" bug. This compounding is a feature for component-internal spacing (padding that scales with that component's own text) and a liability for global typography.

### rem
```css
html { font-size: 16px; } /* the default anyway */
.title { font-size: 2rem; } /* always 32px, regardless of nesting depth */
```
No compounding. One flat reference point. This is why `rem` became the default for font-size, spacing scales, and breakpoints in modern systems — predictable math at any nesting depth.

### %
Behaves differently per property:
- `width: 50%` → 50% of parent's content-box width. Predictable.
- `height: 50%` → only resolves if the parent has an *explicitly defined* height (not `auto`). This trips up nearly every beginner: "why isn't height: 100% working?" — because the ancestor chain up to `html` doesn't have a defined height anywhere.
- `line-height: 150%` vs `line-height: 1.5` — the percentage version locks in a fixed value at that element; the unitless `1.5` recalculates relative to each descendant's own font-size (inherits as a *ratio*, not a value). Unitless is almost always correct.

### vw / vh (and vmin/vmax, dvh)
`1vw` = 1% of viewport width. `100vw` famously overflows horizontally on most pages because it includes the scrollbar's width on some platforms, while `%` on `body` does not. `vh` has its own historical landmine on mobile: `100vh` used to include the address bar, causing content to be cut off. The 2026-current fix is `dvh` (dynamic viewport height), which correctly tracks the *actual* visible viewport as mobile chrome collapses/expands. `svh`/`lvh` (small/large viewport height) exist for edge cases where you want the guaranteed-smallest or guaranteed-largest value instead of the dynamic one.

## Common Misconceptions

- "`px` is more precise/predictable" — it's predictable but *inflexible*; it ignores user accessibility settings, which is the opposite of what "precise" should mean in a real product.
- "`rem` and `em` are basically the same" — no: `rem` has one reference point (root), `em` has a moving reference point (nearest relevant font-size), and that difference is the entire reason both exist.
- "`%` height should just work like `%` width" — it doesn't; height percentages require an explicit ancestor height chain.
- "`vw` for font-size is modern and good" — pure `vw` typography scales with zero minimum/maximum, producing unreadably tiny text on small phones or absurdly large text on ultrawide monitors. This is a `clamp()` problem, not a `vw` problem.

## Current (2026) Best Practice

The modern default is a **hybrid system**, not a single-unit dogma:
- `rem` for font-size, spacing scales, and layout breakpoints (predictable, accessible, respects browser zoom/user font settings)
- `em` for spacing that should scale *with a specific component's own type size* (button padding, icon gaps)
- `%` for fluid widths inside known containers
- `dvh`/`svh` over `vh` for full-height mobile layouts
- `clamp(min, preferred, max)` combining `rem` and `vw` for fluid type that never breaks at the extremes — this is now the standard replacement for naive `vw`-only responsive typography:
```css
h1 { font-size: clamp(1.75rem, 4vw + 1rem, 3.5rem); }
```
Outdated: hardcoding `px` for entire typographic systems, using raw `vw` for font-size without clamping, and using `100vh` unguarded on mobile-facing layouts.

## Why It Matters at a Senior Level

Unit choice is an accessibility and maintainability decision disguised as a syntax detail. A design system built on `px` typography silently breaks for users who increase browser font size for low vision — a WCAG-relevant failure that won't show up in a visual QA pass on your own default-zoom monitor. Seniors get asked to review PRs and catch exactly this: "why did we hardcode px here instead of rem" is a real, common code review comment in mature teams.

## Relevance in React/Next.js Projects

- **Tailwind's scale is rem-based by default** — `text-lg`, `p-4`, etc. compile to `rem` values, not px. Devs who don't understand `rem` misread Tailwind's generated CSS and "fix" it by overriding with arbitrary `px` values (`p-[16px]`), silently breaking the design system's accessibility properties.
- **CSS Modules / styled-components component libraries**: internal component padding is a good `em` use case (`padding: 0.5em 1em` scales with that button's own `font-size` prop) — this is a deliberate pattern in design-system components, not an accident.
- **Next.js `next/font` and root font-size**: teams sometimes override `html { font-size: 62.5%; }` (the old "10px hack" for easy rem math) — this is a legacy pattern that conflicts with some UI libraries' assumptions and should be flagged in review in 2026 codebases.
- **Responsive layouts using CSS Grid/Flexbox with `%` widths** inside client components need an explicit height chain when mixed with `height: 100%` children (e.g., a modal or chat UI stretching to fill a flex parent) — a very common Next.js layout bug.
- **`dvh` vs `vh` matters enormously for mobile-first Next.js apps** (chat interfaces, full-screen modals) — using unguarded `vh` is one of the most common "works on desktop, broken on iOS Safari" bugs shipped to production.

## Relevance in the AI Era

AI coding assistants are fluent in unit *syntax* but not in unit *intent*, which produces subtly wrong-but-compiling code:

- Copilot/Cursor frequently default to `px` when scaffolding new components because it's the statistically dominant unit across all training data (much of which predates the rem-first convention) — it won't proactively choose `rem` unless your codebase's existing patterns strongly signal it via context.
- AI tools commonly generate `height: 100vh` for "full screen" mobile layouts instead of `dvh`, reproducing the exact mobile-Safari address-bar bug that experienced devs specifically learned to avoid — the model doesn't "know" this is currently a live bug class unless prompted with that constraint.
- When asked for "responsive typography," AI often reaches for bare `vw` without `clamp()` bounds, generating text that's technically responsive but breaks at real-world screen extremes — it looks correct in a mid-size preview and fails silently at 320px or 2560px.
- AI can't infer *which* spacing values in your design system are meant to compound (`em`) versus stay fixed (`rem`) — it will happily mix them inconsistently across a component library unless you explicitly constrain it via a design-token prompt or linting rule.

What a dev must still understand manually: which unit should *track* what (root font, parent font, viewport, nothing), why `%` height requires an ancestor chain, and why `dvh`/`clamp()` exist as bug-fixes for specific real-world failure modes — none of which an AI tool will flag as a *problem* in generated code, because syntactically, `100vh` and `16px` are perfectly valid CSS. The bug is invisible to a compiler and invisible to an AI that only checks "does this render." Catching it requires knowing the failure mode exists in the first place.
