# CSS Custom Properties & Theming

## Core Concept

CSS Custom Properties (informally "CSS variables") are author-defined properties, declared with a `--` prefix, that store a value to be reused via `var()`. They are **not** Sass/Less variables — those are compile-time text substitution. Custom properties are runtime, live in the DOM, participate in the cascade, inherit, and can be read/written by JavaScript without a rebuild.

That distinction is the entire reason they matter: theming, dark mode, runtime user preferences, and component-scoped design tokens all became possible in the browser itself, without a CSS-in-JS runtime or a build step re-generating stylesheets.

## Full Mechanics

**Declaration and scope**

```css
:root {
  --brand-color: #4f46e5;
  --spacing-unit: 8px;
}
```

- Custom properties are scoped like any other property — they cascade and inherit through the DOM tree, not through the CSS file structure.
- `:root` is a convention for "global," but it's just the `<html>` element with high specificity. Declaring `--brand-color` on `.card` scopes it to that subtree.
- They are inherited by default (unlike most CSS properties), which is what makes cascading theming possible — a `--theme-bg` set on a parent flows down to every descendant unless overridden.

**Consumption**

```css
.button {
  background: var(--brand-color);
  padding: var(--spacing-unit);
}
```

- `var()` accepts a **fallback**: `var(--brand-color, #333)`. The fallback is used only if the property is *unset* — an invalid value does not fall back to it (see misconceptions below).
- Fallbacks can themselves be custom properties: `var(--accent, var(--brand-color, #333))`.

**Computed at used-value time**

Custom properties are substituted late, not parsed early. This means:

```css
.parent { --gap: 10px; }
.child  { --gap: calc(var(--gap) * 2); margin: var(--gap); }
```

works because `var()` resolution happens per-element, at the point of use, not once globally. This is fundamentally different from preprocessor variables, which resolve once at compile time.

**`@property` — typed custom properties (Baseline, all major engines as of 2024–2025, safe to use in 2026)**

```css
@property --angle {
  syntax: '<angle>';
  inherits: false;
  initial-value: 0deg;
}
```

This is the biggest evolution in this space in recent years. Plain custom properties are untyped strings — the browser doesn't know `--angle` is an angle, so it can't animate or interpolate it. `@property` gives it a real syntax (`<color>`, `<length>`, `<number>`, `<angle>`, etc.), a default `initial-value`, and explicit `inherits` behavior. This unlocks:

- Smooth transitions/animations of custom properties (`transition: --angle 0.3s`), which plain custom props cannot do — the browser treats untyped values as discrete, not interpolable.
- Guaranteed initial values, so `var()` never resolves to nothing unexpectedly.

There's also the JS equivalent, `CSS.registerProperty()`, and the shorthand syntax variant `@property` supports being declared inline via `initial-value` requirements — if `inherits` isn't `false`/`true` and no `initial-value` is given when syntax isn't `*`, the whole rule is invalid and ignored.

**`light-dark()` (Baseline 2024, safe for 2026 use)**

```css
:root {
  color-scheme: light dark;
  --surface: light-dark(#ffffff, #1a1a1a);
}
```

This is now the *current* idiom for theme-aware values without duplicating custom-property blocks under `prefers-color-scheme` media queries. It reads the `color-scheme` property (set on `:root` or via `<meta name="color-scheme">`) and picks the right value automatically, and it composes with manual overrides via `data-theme` attributes or `class`.

**Reading/writing from JavaScript**

```js
el.style.setProperty('--brand-color', '#ef4444');
getComputedStyle(el).getPropertyValue('--brand-color');
```

This is the mechanism behind runtime theming — a theme switcher isn't swapping stylesheets, it's mutating a handful of custom properties on `:root` or a container.

## Common Misconceptions

- **"Invalid values fall back to the `var()` fallback."** False. An invalid value at computed-value time makes the property compute to its *guaranteed-invalid value* (for most properties, this behaves like `unset`/`initial`), not the `var()` fallback — the fallback only applies when the custom property is entirely undeclared.
- **"Custom properties can be used in selectors or media queries."** They cannot (with the narrow, still-limited exception of container query units and some experimental work) — `var()` only works in property values, not in selectors, `@media` conditions, or property *names* themselves.
- **"They're just Sass variables with different syntax."** They're not — no dead-code elimination, no compile-time resolution, they exist in the runtime cascade and can differ per element instance.
- **"Custom properties don't need fallbacks because someone will set `:root`."** In component libraries and design systems, always assume the consumer might not define the token — undefined custom properties silently produce nothing, which is a common source of "invisible" bugs (missing borders, transparent backgrounds).

## 2026 Best Practices vs Outdated Approaches

| Outdated (pre-2023 habit) | Current standard |
|---|---|
| Duplicate `:root` blocks per theme gated by `prefers-color-scheme` | `light-dark()` + a single `color-scheme` declaration, with `data-theme` attribute override for manual toggles |
| SCSS variables for design tokens | CSS custom properties as the source of truth, optionally generated from a JSON/YAML token file by a build tool (Style Dictionary etc.) |
| Untyped custom props for anything animated | `@property` for any custom property that needs to transition/animate |
| Theme switching by swapping `<link>` stylesheets | Theme switching by toggling a `data-theme` attribute/class and letting custom properties cascade |

## Why It Matters at a Senior Level

Custom properties are the mechanism that lets design systems be *runtime-configurable* rather than *build-time-baked*. A senior engineer is expected to reason about: cascade/inheritance interactions (a token defined at the wrong scope silently breaks nested overrides), performance (custom property changes trigger recalculation of every element that consumes them — mass updates on `:root` can be expensive on large trees), and correctness of fallback chains in a multi-tenant/white-label product where tokens may be partially defined.

## Relevance in React/Next.js Projects

- **Theme providers without JS re-renders.** A common React pattern is a `ThemeProvider` context that triggers a full re-render tree on theme change. With custom properties, you instead toggle `data-theme="dark"` on `<html>` (often in a Next.js `layout.tsx` via a small inline script to avoid flash-of-wrong-theme) and let CSS cascade — zero component re-renders needed for color changes.
- **Avoiding hydration mismatch / FOUC in Next.js.** Reading `prefers-color-scheme` or `localStorage` in a `useEffect` to set theme causes a flash because the server-rendered HTML doesn't know the client's preference. The current fix is a tiny synchronous inline `<script>` in the `<head>` (before hydration) that sets the `data-theme` attribute or the `color-scheme` custom property directly on `documentElement`, sidestepping React entirely for this concern.
- **CSS Modules + custom properties for component-scoped tokens.** In a `Button.module.css`, exposing `--button-bg` as a custom property lets consumers override it per-instance via inline `style={{ '--button-bg': color }}` in JSX — this is the idiomatic way to make a styled component themeable without prop-drilling variant classes, and it's fully compatible with Server Components since it's pure CSS.
- **Tailwind v4's CSS-first theming.** Tailwind v4 (current major as of 2026) generates utility classes directly from `@theme` blocks built on custom properties, meaning your design tokens *are* custom properties under the hood — understanding this is necessary to override Tailwind tokens at runtime (e.g., white-labeling a Next.js multi-tenant app) rather than fighting the utility layer.
- **Gotcha with CSS-in-JS / styled-components in RSC.** Runtime CSS-in-JS libraries that inject `<style>` tags via JS don't play well with React Server Components (no client JS execution at render). Custom properties, being plain CSS, work identically in Server and Client Components — this is a real architectural reason teams are moving theming logic *out* of JS-based styling and into custom properties.

## Relevance in the AI Era

- **AI assistants default to outdated theming patterns.** Ask Copilot/Cursor for "dark mode toggle" and it will often generate duplicated `:root` / `[data-theme="dark"]` blocks with every token repeated, or reach for a `prefers-color-scheme` media query alone — missing `light-dark()` and `color-scheme`, which is the more current, less redundant approach. It's syntactically valid, so it won't get flagged by a linter or TypeScript — only a dev who knows the current idiom will recognize the duplication as a maintenance smell.
- **AI tools frequently misuse `var()` fallbacks.** Generated code often assumes an invalid value (e.g., an empty string interpolated into a template) will gracefully fall back via `var(--x, fallback)`. It won't — invalid computed values behave like `unset`, not "undefined." This produces subtly broken UI (missing background, invisible text) that passes visual smoke-testing in the AI's own quick check but breaks in edge cases the assistant didn't consider.
- **Animation requests silently fail without `@property`.** If you ask an AI agent to "animate this gradient angle" or "transition between two arbitrary colors stored in variables," it may write `transition: --angle 0.3s` without emitting the required `@property` registration — the code looks correct, compiles, and does nothing, because untyped custom properties can't interpolate. Catching this requires knowing that transitions on custom properties have a hard prerequisite the AI often omits.
- **Agentic refactors break inheritance scope silently.** When an autonomous coding agent "cleans up" CSS by moving a custom property declaration from `:root` into a component file (or vice versa) during a refactor, it can unintentionally change inheritance scope — a token that worked globally now only resolves inside one subtree, and everything outside falls back to nothing. This is invisible in a diff review unless the reviewer understands cascade/inheritance semantics, not just "the variable name still matches."
- **Why this doesn't become obsolete:** AI tools produce fluent CSS syntax, but theming bugs here are semantic (cascade scope, invalid-vs-undefined, missing type registration for animation) rather than syntactic. A dev who doesn't understand custom-property mechanics can't tell a working theme system from one that silently degrades for a subset of users — the code will look plausible and pass a cursory glance either way.
