# Responsive Design: Media & Container Queries
**Pillar:** Foundations Done Right | **Category:** HTML & CSS | **Level:** Advanced

## Core Concept

Responsive design has two fundamentally different questions baked into it, and most devs still conflate them:

1. **"What does the viewport look like?"** → Media queries.
2. **"What space does *this specific element* have to work with?"** → Container queries.

For over a decade we only had an answer to question one. That forced a bad habit: designing components as if they only ever live at one place in the layout, keyed to *screen* size instead of *available* size. A card component styled with `@media (min-width: 768px)` breaks the moment you drop it into a narrow sidebar on a wide screen — because the query never asked about the sidebar, it asked about the monitor.

Container queries fix this by letting an element respond to the size of its nearest **containment context**, not the viewport. This is the single biggest shift in CSS responsive thinking since flexbox.

## Media Queries — Full Mechanics

A media query evaluates **viewport/device characteristics** and conditionally applies a ruleset.

```css
@media (min-width: 768px) { ... }
@media (max-width: 767.98px) { ... }
```

**Range syntax (current standard, not just a nicety anymore):**
```css
@media (768px <= width < 1024px) { ... }
@media (width > 600px) { ... }
```
This reads like actual math and removes the old `min-width`/`max-width` boundary-fencepost bugs (the classic 767 vs 768 off-by-one).

**Beyond width**, the queries seniors are expected to know cold:
- `prefers-color-scheme: dark | light`
- `prefers-reduced-motion: reduce`
- `prefers-contrast: more | less | no-preference`
- `hover: hover | none` and `pointer: fine | coarse | none` — critical for distinguishing "small screen" from "touch device" (a touchscreen laptop is neither purely mobile nor purely desktop)
- `orientation: portrait | landscape`
- `resolution` — for serving sharper assets, distinct from `srcset`/`sizes`
- `aspect-ratio` — media queries can key off element/viewport aspect ratio too

**Combining conditions:**
```css
@media screen and (min-width: 768px) and (prefers-color-scheme: dark) { ... }
```

## Container Queries — Full Mechanics

Container queries require you to explicitly opt an ancestor into being a **query container**:

```css
.card-wrapper {
  container-type: inline-size; /* query against the inline (width) axis */
  container-name: card;        /* optional, but required if you need to target a specific container */
}

@container card (min-width: 400px) {
  .card-title { font-size: 1.5rem; }
}
```

`container-type` values matter:
- `inline-size` — the standard choice; contains layout along the inline axis only, enables width-based queries. Cheapest performance cost.
- `size` — contains both axes, enables height queries too, but forces the container to lose its intrinsic size in that axis (you often must set an explicit height). Used far less.
- `normal` — default, not a query container.

**Container query units** — the part creators most often skip and shouldn't:
- `cqw`, `cqh` — % of container's width/height
- `cqi`, `cqb` — % of container's inline/block size (logical, writing-mode aware — prefer these over cqw/cqh in 2026 codebases)
- `cqmin`, `cqmax` — smaller/larger of the two

```css
.card-title { font-size: clamp(1rem, 5cqi, 2rem); }
```

**Style queries** (`@container style(...)`) are the newer, less-known extension: querying a container based on a *custom property value* rather than size, letting components branch styling off design tokens or state passed as CSS variables — not just dimensions.

## Common Misconceptions

- **"Container queries replace media queries."** No — media queries still own viewport-level concerns (color scheme, reduced motion, pointer type, print). Container queries own component-level layout. Senior-level responsive CSS uses both, deliberately, for different jobs.
- **"I need a wrapper `<div>` just for `container-type`."** Often true, but not always — sometimes an existing semantic parent can be promoted to a container. Adding an unnecessary wrapper is itself a smell worth catching.
- **"Container queries need a fallback for old browsers."** As of 2026 they're broadly supported across evergreen browsers; the meaningful conversation now is graceful degradation of the *value*, not universal polyfilling.
- **"Fewer breakpoints = better."** Fluid, `clamp()`-driven sizing reduces the *number* of discrete breakpoints needed, but doesn't eliminate the need for structural breakpoints where layout genuinely changes shape (grid to stack, nav collapse, etc.).

## 2026 Best Practice vs Outdated Approach

| Outdated | Current |
|---|---|
| Desktop-first cascades with `max-width` overrides | Mobile-first, `min-width` up, with range syntax where it clarifies intent |
| Device-specific breakpoints (`375px` for "iPhone") | Content-driven breakpoints: query wherever the design actually breaks |
| JS `resize` listeners / `ResizeObserver` for component layout | `container-type` + `@container` for the vast majority of component-level responsiveness |
| Fixed `font-size` per breakpoint | `clamp()` fluid typography, container query units for component-local scaling |
| One giant global breakpoint set imported everywhere | Component-owned container queries; global breakpoints reserved for page-level shell/nav decisions |

## Why This Matters at a Senior Level

Junior responsive CSS asks "does this look right on my three test screen widths." Senior responsive CSS asks "does this component look right in *every context it will ever be dropped into*, including ones that don't exist yet" — a sidebar today, a modal tomorrow, a dashboard widget next quarter. Container queries make components genuinely reusable in a way media-query-only design never could. Reviewing for this is a real interview signal in 2026: can a candidate explain *when* to reach for a container query over a media query, not just that both exist.

## Relevance in React/Next.js Projects

- **Design systems / component libraries**: any shared component (`Card`, `Table`, `StatBlock`) that must work in multiple layout slots should own its container query, not inherit page-level media query assumptions. This is a direct component-API decision, not just styling.
- **Tailwind CSS**: the `@container` variant (`@sm:`, `@lg:` prefixed with a container context) mirrors this natively — teach viewers that adding `className="@container"` to a wrapper is the Tailwind equivalent of `container-type: inline-size`, and forgetting it is the #1 reason "my container variants aren't working" bugs show up in React codebases.
- **CSS Modules / CSS-in-JS**: styled-components/vanilla-extract users need to know container queries are plain CSS — no JS runtime cost, unlike the old pattern of measuring a ref with `ResizeObserver` and setting state to drive conditional class names. That old pattern causes extra re-renders and layout thrash; container queries eliminate an entire category of "why is this component re-rendering on resize" performance bugs.
- **Next.js layouts/slots**: with parallel routes and nested layouts, the same component can render inside differently-sized regions depending on route composition — container queries are what make that composition safe without prop-drilling a "variant" size prop.
- **Server Components**: container queries are pure CSS and resolve client-side after hydration with no JS dependency, which matters when you're intentionally keeping a component a Server Component and can't reach for `useEffect`/`ResizeObserver` at all.

## Relevance in the AI Era

- AI assistants overwhelmingly default to **fixed, memorized breakpoints** (`320px`, `768px`, `1024px`, `1440px`) pulled from training-data habits, regardless of the actual content's break points. It's syntactically valid CSS that's semantically wrong for the design — you still need to know how to find the *real* break point by resizing content, not trusting a generated number.
- AI tools frequently **reach for a media query when a container query is the correct tool**, especially for "make this card responsive" prompts, because container queries are newer and underrepresented relative to media queries in training data. Catching this requires knowing the distinction yourself — the AI won't flag its own category error.
- When AI *does* generate container queries, it commonly **forgets to set `container-type` on the ancestor**, producing a `@container` rule that silently does nothing. This fails silent, not loud — no console error, just a rule that never applies. A dev who doesn't understand containment context will waste time debugging the wrong layer.
- AI-generated code still frequently reaches for **JS-based resize detection** (`ResizeObserver` + state) for problems container queries now solve in pure CSS — it's not wrong, but it's outdated and adds unnecessary re-renders. Reviewers need to recognize when a CSS-only solution should replace a JS one.
- None of this becomes obsolete because AI can produce the syntax: the actual skill is knowing **which layer of "responsive" a given problem belongs to** — viewport, container, or content-level (`clamp()`/intrinsic sizing) — and AI has no way to infer that from a vague prompt like "make it responsive." That judgment call is still entirely on the dev reviewing the diff.
