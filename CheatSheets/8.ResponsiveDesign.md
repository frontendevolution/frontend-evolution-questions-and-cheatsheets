# Responsive Design: Media & Container Queries — The Complete Reference

_Foundations Done Right → HTML & CSS → Advanced_

---

## 1. Core Definitions & Vocabulary

- **Media Query (MQ)**: a conditional CSS rule that applies styles based on characteristics of the _viewport/device_ — width, orientation, color scheme, etc.
- **Container Query (CQ)**: a conditional CSS rule that applies styles based on characteristics of an element's _containing element_, independent of the viewport.
- **Containment context**: the ancestor element you opt into being "queryable" via `container-type`. A component queries its container, not the page.
- **Breakpoint**: the specific value at which a query's condition flips true/false. Not a fixed set of numbers — it should be wherever _your content_ breaks, not a device you're targeting.
- **Intrinsic vs extrinsic sizing**: containers with intrinsic size queries can create sizing loops (see Gotchas) — this is why `container-type: size` needs an explicit size on the container itself.
- **Discrete vs Range media features**: some features (`orientation`, `pointer`) only take discrete keyword values; others (`width`, `resolution`) are ranged and support comparison operators.
- **Style queries**: a newer, less-supported CQ variant — query a container's _custom property value_ (e.g. `container-type` not required, but `container-name` is), not its size.

## 2. Media Queries — Full Syntax Surface

```css
/* Basic */
@media screen and (min-width: 768px) { }

/* Range syntax (Media Queries Level 4 — current standard) */
@media (width >= 768px) and (width < 1200px) { }
@media (400px <= width <= 700px) { }

/* Old-style min/max (still valid, still widely used) */
@media (min-width: 768px) and (max-width: 1199px) { }

/* Logical operators */
@media screen and (min-width: 768px) { }        /* AND */
@media (min-width: 768px), (orientation: landscape) { }  /* OR (comma) */
@media not screen and (min-width: 768px) { }     /* NOT (negates whole query) */
@media only screen and (min-width: 768px) { }    /* legacy — masks old browsers, not needed today */

/* Nesting inside a selector (CSS Nesting, current) */
.card {
  @media (width >= 768px) { display: grid; }
}

/* JS matching */
const mq = window.matchMedia('(min-width: 768px)');
mq.matches;                 // boolean, current state
mq.addEventListener('change', e => { e.matches });

/* In markup */
<link rel="stylesheet" media="(min-width: 768px)" href="wide.css">
<img srcset="s.jpg 480w, l.jpg 1080w" sizes="(min-width: 768px) 50vw, 100vw">

/* In imports (rarely used — blocks rendering, avoid) */
@import url("wide.css") (min-width: 768px);
```

## 3. Media Types (exhaustive — current spec)

| Type     | Meaning                                            |
| -------- | -------------------------------------------------- |
| `all`    | Default. Applies to all devices.                   |
| `screen` | Screens (the overwhelming majority of real usage). |
| `print`  | Print preview / printed output / print-to-PDF.     |
| `speech` | Screen readers and speech synthesizers.            |

> Deprecated and removed from the spec (still parsed for backward-compat but always evaluate to no-match or `all`): `tty`, `tv`, `projection`, `handheld`, `braille`, `embossed`, `aural`. Never use these.

## 4. Media Features (exhaustive — current spec)

**Viewport / display geometry**

- `width` / `min-width` / `max-width` — viewport width.
- `height` / `min-height` / `max-height` — viewport height.
- `aspect-ratio` — viewport width÷height ratio.
- `orientation` — `portrait` or `landscape`.
- `device-width` / `device-height` — ⚠️ deprecated, screen (not viewport) size. Don't use.

**Display quality**

- `resolution` — pixel density (`dpi`, `dpcm`, or `x`/`dppx`). Key for high-DPI image swaps.
- `color` — bits per color component of output device.
- `color-index` — number of entries in the device's color lookup table (legacy, indexed color displays).
- `color-gamut` — `srgb` / `p3` / `rec2020`, how wide a color range the display supports.
- `monochrome` — bits per pixel on a monochrome device (0 if not monochrome).
- `dynamic-range` / `video-dynamic-range` — `standard` vs `high` (HDR detection).
- `grid` — whether output device is grid-based (e.g. terminal) vs bitmap.
- `scan` — `interlace` / `progressive`, TV-only, effectively obsolete.

**Interaction capability**

- `pointer` — primary pointer precision: `none` / `coarse` (touch) / `fine` (mouse/stylus).
- `hover` — can the primary input hover: `none` / `hover`.
- `any-pointer` — like `pointer` but considers _all_ available pointers, not just primary.
- `any-hover` — like `hover` but considers all input mechanisms.

**User preferences (OS/browser-level settings)**

- `prefers-color-scheme` — `light` / `dark` / `no-preference`.
- `prefers-reduced-motion` — `reduce` / `no-preference`.
- `prefers-contrast` — `no-preference` / `more` / `less` / `custom`.
- `prefers-reduced-transparency` — `reduce` / `no-preference`.
- `prefers-reduced-data` — `reduce` / `no-preference` (Save-Data signal; limited support).
- `forced-colors` — `active` / `none` (Windows High Contrast Mode).
- `inverted-colors` — `inverted` / `none` (Safari-specific, color inversion accessibility setting).

**Environment / scripting**

- `update` — how often the layout can update: `none` (printed) / `slow` (e-ink) / `fast` (screen).
- `overflow-block` — how the device handles block-axis overflow: `none` / `scroll` / `optional-paged` / `paged`.
- `overflow-inline` — whether inline-axis overflow can scroll: `none` / `scroll`.
- `scripting` — `none` / `initial-only` / `enabled` — is JS available.
- `display-mode` — `browser` / `standalone` / `fullscreen` / `minimal-ui` / `window-controls-overlay` — PWA display context.

## 5. Container Queries — Full Syntax Surface

```css
/* Step 1: opt an element into being a query container */
.card-wrapper {
  container-type: inline-size; /* most common — queries inline (width) axis only */
  /* container-type: size; */ /* queries both axes — requires explicit height */
  /* container-type: normal; */ /* default — not a size container, but can still be a style-query container */
  container-name: card; /* optional — scopes which query targets this container */
  /* shorthand */
  container: card / inline-size;
}

/* Step 2: query it from a descendant */
@container card (min-width: 400px) {
  .card-title {
    font-size: 1.5rem;
  }
}

/* Unnamed query — matches nearest ancestor container of any name */
@container (min-width: 400px) {
}

/* Range syntax works here too */
@container (400px <= width <= 800px) {
}

/* Style queries (newer, check support) — query a custom property's computed value */
@container style(--theme: dark) {
  .card {
    background: black;
  }
}

/* Container query units — scoped to nearest queried container */
.card-title {
  font-size: clamp(1rem, 5cqi, 2rem);
}
```

---

## 6. Container Query Units (exhaustive)

| Unit    | Meaning                                                         |
| ------- | --------------------------------------------------------------- |
| `cqw`   | 1% of container's width                                         |
| `cqh`   | 1% of container's height                                        |
| `cqi`   | 1% of container's inline-size (logical — respects writing mode) |
| `cqb`   | 1% of container's block-size (logical)                          |
| `cqmin` | smaller of `cqi` / `cqb`                                        |
| `cqmax` | larger of `cqi` / `cqb`                                         |

Prefer `cqi`/`cqb` over `cqw`/`cqh` in modern code — they respect writing-mode/direction, matching how `inline-size`/`block-size` already work elsewhere in CSS.

## 7. Container Query Features (queryable conditions)

`width`, `min-width`, `max-width`, `height`, `min-height`, `max-height`, `inline-size`, `block-size`, `aspect-ratio`, `orientation`. (Same shape as media features, but evaluated against the container box, not the viewport.)

## 8. Internal Mechanics — How Evaluation Actually Works

**Media Queries**

1. Parsed at stylesheet load; re-evaluated on viewport resize, orientation change, zoom, or a monitored feature changing (e.g. OS switches dark mode).
2. Each `@media` block is evaluated independently and applied as a normal cascade layer — normal specificity/source-order rules apply _within_ matching queries, but a matching MQ doesn't out-rank non-MQ rules by itself.
3. `matchMedia()` gives you a live `MediaQueryList` — check `.matches` once, or subscribe via `change` for reactive JS behavior without polling `resize`.

**Container Queries**

1. `container-type: inline-size` (or `size`) takes the element out of normal size-based layout dependencies for its descendants' queries and establishes both containment (`contain: layout style` implicitly, plus size containment on the queried axis) and a query context.
2. The browser lays out the container first, gets its size, _then_ resolves descendant `@container` rules and re-lays-out affected descendants — this is why deeply nested container-size dependencies can be expensive (see Performance).
3. `container-type: size` is the trap: it applies size containment on **both** axes, meaning the container can no longer size itself based on its content (that would be a circular dependency — "how tall am I" depends on "what do children look like" which depends on "how tall is my container"). You must give it an explicit height or it collapses to zero.
4. `container-type: inline-size` avoids that loop by only containing the inline axis — block-size (height) can still be intrinsic/content-driven, which is why it's the default recommendation.
5. `@container` queries the **nearest ancestor** that is a valid container matching the given `container-name` (or nearest of any name if unnamed) — not a fixed global container.

## 9. Common Mistakes & Gotchas

- Using `container-type: size` without setting an explicit height → content collapses to 0px (the circular-dependency trap above).
- Forgetting `container-type` entirely and querying a container that was never opted in — the `@container` rule silently never matches, no error thrown.
- Assuming container queries replace media queries — they solve different axes: CQ = component/context, MQ = viewport/device/user-preference. You need both.
- Mixing up `cqw` (viewport-style %) with `cqi` (logical, writing-mode-aware) and getting unexpected results in RTL or vertical writing modes.
- Writing `@media (min-width: 768px)` breakpoints based on _device names_ ("iPad breakpoint") instead of where your actual layout breaks — device dimensions change every year, your content's break points don't.
- Forgetting `prefers-reduced-motion` entirely — animation-heavy UI ships with zero respect for vestibular-disorder users by default.
- Querying `hover`/`pointer` as a _device_ detector ("if hover, it's desktop") — hybrid touchscreen laptops and touch-with-mouse setups break that assumption.
- Container-querying an element for width while its own width is `auto`/shrink-to-fit inside a flex/grid parent — sizing feedback loops and thrashing.
- Style queries (`@container style(...)`) used before checking support — they're newer than size-based container queries and not universal yet.
- Overriding `container-type: inline-size` on an element with `display: inline` — inline-level boxes largely don't establish size containment the way you'd expect; you almost always want the container to be block-level or a flex/grid item.

## 10. Best Practices

- Default to `container-type: inline-size` for components; reach for `container-type: size` only when you deliberately need block-axis queries and can guarantee an explicit height.
- Name containers (`container-name`) once you have more than one nested queryable ancestor, so descendant queries target the _intended_ container, not the nearest accidental one.
- Set breakpoints from content, not device catalogs — resize until the layout looks bad, that's your breakpoint.
- Pair `prefers-reduced-motion`, `prefers-color-scheme`, and `prefers-contrast` queries as default-on accessibility affordances, not optional extras.
- Use range syntax (`width >= 768px`) over legacy `min-width`/`max-width` in new code — it's more readable for compound ranges and is current baseline-supported.
- Use container queries for reusable components (cards, sidebars, widgets dropped into unknown contexts) and media queries for page-level/global layout shifts.
- Combine `clamp()` with `cqi` for fluid, container-relative typography instead of hardcoding font-size per breakpoint.

---

## 11. Anti-Patterns

- "Bootstrap-brain" fixed breakpoints (`576px`/`768px`/`992px`/`1200px`) applied blindly without checking if your content actually breaks there.
- Container-querying the `<body>` or a page-level wrapper — that's just a media query with extra steps; use MQ for viewport-level decisions.
- Deeply nested container queries where a grandchild queries a container three levels up by name — fragile coupling, breaks silently if markup structure shifts.
- Using JS-based resize listeners (`ResizeObserver`, `window.resize`) to fake container-query behavior in 2026 — native CQ support is baseline; the JS workaround is now legacy debt.
- Applying `display: none` inside a media/container query to "fix" a layout instead of restructuring — hides the symptom, keeps the element in the DOM/accessibility tree in ways that confuse assistive tech.

## 12. Media Queries vs Container Queries — Direct Comparison

|                                                     | Media Query                                                                               | Container Query                                             |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Evaluates                                           | Viewport / device / user OS preference                                                    | Nearest ancestor container's box size (or style)            |
| Reusability across contexts                         | Poor — component looks different depending on _where_ it's used at a given viewport width | Excellent — component adapts to whatever box it's placed in |
| Requires opt-in element                             | No                                                                                        | Yes (`container-type`)                                      |
| Can query preferences (dark mode, motion, contrast) | Yes                                                                                       | No                                                          |
| Can query pointer/hover capability                  | Yes                                                                                       | No                                                          |
| Typical use case                                    | Global page layout, accessibility preferences, print styles                               | Reusable components (cards, widgets, sidebars)              |

## 13. Performance Implications

- Media query re-evaluation on resize is cheap and throttled by the browser's own layout/reflow scheduling — not a real perf concern in practice.
- Container queries force a layout dependency: the browser must size the container before resolving descendant styles, which can mean an extra layout pass for deeply nested or highly dynamic container trees.
- `container-type: size` (containing both axes) is more expensive than `inline-size` because it removes more of the browser's ability to short-circuit layout work.
- Excessive `matchMedia` listeners with heavy JS callbacks on `change` can cause jank during resize/rotation — debounce or keep the callback cheap.
- `@import` with a media condition still blocks initial render in most engines regardless of the query's match state — avoid for critical CSS.
- Container query units (`cqi`, etc.) recompute on every container resize just like `%`/`vw` — no meaningfully different cost profile than existing relative units.

## 14. Browser & Runtime Support Notes

- Media queries (including Level 4 range syntax `<=`/`>=`) are baseline-supported across all evergreen browsers.
- Size-based container queries (`container-type`, `@container`, `cq*` units) are baseline-supported across all major evergreen browsers as of the last two major versions of each.
- Style queries (`@container style(...)`) have materially newer, less consistent support than size queries — verify current caniuse status before relying on them for production-critical UI, and provide a fallback.
- `prefers-reduced-data` has the weakest support of the user-preference features — treat it as progressive enhancement, never a sole gate.
- Legacy media types (`tv`, `handheld`, etc.) are ignored/no-op everywhere — don't rely on them, don't worry about "supporting" them either.
- Always verify exact current version numbers on caniuse.com at build time for anything you're about to ship to production — "baseline" status shifts as older browser versions age out of support windows.

---

## 15. Security Implications

- Media queries can leak environment info to attackers via CSS-based side channels historically (e.g. `prefers-color-scheme` or `resolution` used with `@import` timing/`background-image` requests to fingerprint or exfiltrate state) — treat CSS-conditional resource loading as a data-exfiltration surface if you ever conditionally load external resources based on user-controlled state.
- `prefers-color-scheme`/`prefers-reduced-motion`/etc. are part of the passive fingerprinting surface (combined with other signals) — not a vulnerability per se, but relevant if your threat model includes user tracking/fingerprinting resistance.
- Container queries have no meaningful attack surface of their own — they operate purely on layout geometry, not user data.
- Never use CSS media/container conditions as an actual access-control or content-gating mechanism (e.g. "hide admin panel via `@media`") — CSS is inspectable/overridable client-side; this is a client-side-only "hide," not a security boundary.

---

## 16. Accessibility Implications

- `prefers-reduced-motion: reduce` should gate all non-essential transitions/animations — required for users with vestibular disorders, not a nice-to-have.
- `prefers-contrast: more` should be honored for users needing stronger visual differentiation — pair with sufficient color contrast ratios regardless.
- `forced-colors: active` (Windows High Contrast Mode) can strip custom colors entirely — test your UI under it; icons/borders relying purely on color can disappear.
- `prefers-color-scheme` respects OS-level accessibility/visual comfort settings — don't override it with a JS-only theme toggle that ignores the OS preference on first load.
- Responsive layout shifts (via either MQ or CQ) must preserve a logical reading/focus order — reflowing visually without reordering the DOM can create a mismatch between visual order and keyboard/screen-reader order.
- Ensure touch targets remain accessible-sized (44×44px+ recommendation) across all breakpoints, not just the largest one.

## 17. Minimal Working Example

```css
/* Page-level: viewport & preference driven */
@media (prefers-color-scheme: dark) {
  :root {
    --bg: #111;
    --fg: #eee;
  }
}
@media (width >= 1024px) {
  .layout {
    grid-template-columns: 240px 1fr;
  }
}

/* Component-level: container driven, reusable anywhere */
.card-wrapper {
  container-type: inline-size;
  container-name: card;
}
@container card (min-width: 360px) {
  .card {
    display: grid;
    grid-template-columns: 96px 1fr;
    gap: 1rem;
  }
  .card-title {
    font-size: clamp(1rem, 4cqi, 1.5rem);
  }
}
```

## 18. Rapid-Fire Interview One-Liners

- Media queries respond to the viewport; container queries respond to a queried ancestor's box.
- `container-type: size` contains both axes and needs an explicit height, or content collapses.
- `container-type: inline-size` only contains the inline axis — the safe default for most components.
- `cqi`/`cqb` are logical (writing-mode aware); `cqw`/`cqh` are physical.
- Range syntax (`width >= 768px`) is the current preferred way to write comparison queries.
- `prefers-reduced-motion`, `prefers-color-scheme`, `prefers-contrast` are OS-level user preferences exposed to CSS, not device capabilities.
- `hover`/`pointer` describe input _capability_, not device _category_ — don't infer "mobile" from them.
- A component can't container-query itself — only a descendant can query an ancestor container.
- Style queries let you branch on a custom property's value, not just size — newer, check support before relying on it.
- CSS conditions are never a security boundary — they're presentation only.

## 19. In React/Next.js Projects

- Container queries are the natural fit for shared component libraries (`<Card>`, `<Sidebar>`) that get dropped into unknown layout contexts across a Next.js app — style with `@container` inside the component's own CSS/CSS Module instead of prop-drilling a `size` variant.
- With CSS Modules or Tailwind, apply `container-type: inline-size` on the component's root wrapper class, not on the component's outermost DOM node if that node itself needs to participate in a parent flex/grid layout — an extra wrapper `div` is often the pragmatic fix.
- Server Components render with zero knowledge of runtime viewport/container size — you cannot conditionally render _different JSX_ based on a media/container query on the server; MQ/CQ only control _styling_, not the render tree, unless paired with a client-side `matchMedia`/`ResizeObserver` hook (which forces that piece to be a Client Component).
- If a component genuinely needs different _markup_ (not just style) per size, that logic has to live in a `'use client'` component using `matchMedia` or `ResizeObserver`, accepting a hydration flash before the first client-side measurement completes — plan a sensible SSR default.
- Tailwind's default breakpoints (`sm`/`md`/`lg`/`xl`/`2xl`) are viewport-based media queries under the hood; Tailwind's container query plugin/`@min-*`/`@max-*` variants (current versions) map directly onto native `@container` — don't hand-roll a JS resize hook when the utility classes already cover it.
- Avoid `window.matchMedia` calls during the render phase of a component — they run at import/render time on the server where `window` doesn't exist, causing a hydration error; gate them inside `useEffect` or a custom hook with an SSR-safe initial value.
- CSS-in-JS libraries (styled-components, vanilla-extract, Panda CSS) all support container queries now — verify your specific library's current version actually forwards `container-type`/`@container` correctly rather than stripping it, since support lagged behind plain CSS.
- next/image's `sizes` prop is itself a media-query-driven API (`sizes="(min-width: 768px) 50vw, 100vw"`) — get this wrong and you silently ship oversized images at every breakpoint, hurting LCP.

## 20. In the AI Era

- AI assistants very frequently default to `container-type: size` when `inline-size` was the correct, safer choice — this ships the zero-height collapse bug, and the AI rarely adds the explicit height that `size` requires. **You must manually verify which containment axis was actually needed.**
- AI-generated responsive code overwhelmingly defaults to legacy fixed breakpoints (`576/768/992/1200`) memorized from older training data/tutorials, rather than reasoning about where _this specific_ layout actually breaks — you still need to eyeball the resize and adjust the numbers yourself.
- AI tools frequently mix media queries and container queries interchangeably as if they're the same tool, e.g. suggesting `@container` for a page-level dark-mode toggle (wrong tool — that's a media/preference query, containers can't see OS preferences at all) — a plausible-looking `@container (prefers-color-scheme: dark)` is not valid syntax and won't work.
- AI-generated components frequently forget the `container-type` opt-in on the ancestor entirely while writing a perfectly correct `@container` rule on the descendant — the rule silently never fires, and there's no console error to catch it, so it must be checked visually.
- AI code that mixes `cqw`/`vw` and `cqi` inconsistently within the same component is common — subtly wrong in RTL layouts or vertical writing modes, and AI review rarely flags writing-mode implications since it isn't reasoning about internationalization by default.
- Accessibility-related media features (`prefers-reduced-motion`, `prefers-contrast`, `forced-colors`) are the _first_ thing AI-generated animation-heavy code omits unless explicitly prompted for them — you must manually add and test these; don't assume the AI included them just because the component "looks done."
- In Next.js specifically, AI assistants often generate `matchMedia`/`ResizeObserver` logic directly in a component body without gating it behind `'use client'` or a `useEffect`, producing a hydration mismatch or a build error on `window is not defined` — this is one of the most common AI-introduced Next.js bugs around responsive logic, and it requires understanding the server/client render boundary to catch, not just reading the CSS.
- This topic doesn't get obsoleted by AI code generation because the _judgment calls_ — which axis to contain, where the real breakpoint is, which accessibility preferences apply, whether MQ or CQ is the right primitive for a given decision — are context- and content-dependent decisions AI can't make correctly from a prompt alone; it can produce syntactically valid CSS for the wrong strategy just as easily as the right one, and only someone who understands the mechanics can tell the difference by reading the code, not just running it.
