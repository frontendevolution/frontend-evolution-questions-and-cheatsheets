# Box Model, Display & Positioning — The Complete Reference

**Pillar:** Foundations Done Right | **Category:** HTML & CSS | **Level:** Beginner → Senior nuance

---

## 1. Core Definitions & Vocabulary

- **Box model** — every rendered element is a rectangular box made of content, padding, border, and margin.
- **Containing block** — the ancestor box against which an element's size/position percentages and offsets are calculated.
- **Normal flow** — the default layout order (block stacks vertically, inline flows horizontally) before any positioning is applied.
- **Formatting context** — an independent layout environment (Block Formatting Context, Flex Formatting Context, Grid Formatting Context) that decides how children inside it are laid out and interact with siblings/floats.
- **Stacking context** — a self-contained layer for z-ordering; elements only compete on z-index with siblings inside the same stacking context.
- **Out-of-flow element** — anything with `position: absolute`, `position: fixed`, or `float` — removed from normal flow, no longer affects sibling layout.
- **Replaced element** — an element whose content is rendered outside CSS (e.g. `<img>`, `<video>`, `<input>`) — box model behaves slightly differently (intrinsic sizing).

---

## 2. The Box Model — Full Layer Breakdown

From innermost to outermost:

1. **Content box** — the actual text/image/inline content area.
2. **Padding box** — `padding-top/right/bottom/left` (or `padding` shorthand) — space between content and border, same background as the element.
3. **Border box** — `border-width`, `border-style`, `border-color` (or `border` shorthand) — a visible or invisible edge.
4. **Margin box** — `margin-top/right/bottom/left` (or `margin` shorthand) — transparent space outside the border, affects spacing between elements.

**Total rendered width (content-box default):**
`width + padding-left + padding-right + border-left-width + border-right-width`
(margin is NOT part of the element's own box — it affects surrounding layout only)

---

## 3. `box-sizing` — Full Syntax

```css
box-sizing: content-box; /* default — width/height apply to content only */
box-sizing: border-box; /* width/height include padding + border */
box-sizing: inherit;
box-sizing: initial;
box-sizing: revert;
box-sizing: revert-layer;
box-sizing: unset;
```

- `content-box` (default): `width` = content only. Padding/border added on top → total size grows.
- `border-box`: `width` = content + padding + border. Content area shrinks to fit. Industry-standard reset:

```css
*,
*::before,
*::after {
  box-sizing: border-box;
}
```

## 4. `display` — Full Enumerated Value List

Modern CSS uses a **two-value syntax** (`display: <outer> <inner>`) under the hood, but browsers still accept legacy single-keyword values, which map as shown:

| Value                 | Outer/Inner equivalent | Behavior                                                                                                                                      |
| --------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `block`               | `block flow`           | Full available width, stacks vertically, respects all box model properties                                                                    |
| `inline`              | `inline flow`          | Flows in text line, ignores width/height/vertical margin                                                                                      |
| `inline-block`        | `inline flow-root`     | Flows inline, respects width/height/margin like a block                                                                                       |
| `flex`                | `block flex`           | Block-level flex container — one-dimensional child layout                                                                                     |
| `inline-flex`         | `inline flex`          | Inline-level flex container                                                                                                                   |
| `grid`                | `block grid`           | Block-level grid container — two-dimensional child layout                                                                                     |
| `inline-grid`         | `inline grid`          | Inline-level grid container                                                                                                                   |
| `flow-root`           | `block flow-root`      | Block box that establishes a new Block Formatting Context (modern float/margin-collapse containment fix)                                      |
| `contents`            | —                      | Element's box disappears; children render as if the parent didn't exist (removes it from box tree, keeps it in accessibility tree by default) |
| `none`                | —                      | Element and all descendants removed from render tree entirely — no box generated at all                                                       |
| `table`               | `block table`          | Behaves like `<table>`                                                                                                                        |
| `inline-table`        | `inline table`         | Behaves like `<table>` but inline-level                                                                                                       |
| `table-row`           | —                      | Behaves like `<tr>`                                                                                                                           |
| `table-cell`          | —                      | Behaves like `<td>`                                                                                                                           |
| `table-column`        | —                      | Behaves like `<col>`                                                                                                                          |
| `table-column-group`  | —                      | Behaves like `<colgroup>`                                                                                                                     |
| `table-header-group`  | —                      | Behaves like `<thead>`                                                                                                                        |
| `table-footer-group`  | —                      | Behaves like `<tfoot>`                                                                                                                        |
| `table-row-group`     | —                      | Behaves like `<tbody>`                                                                                                                        |
| `table-caption`       | —                      | Behaves like `<caption>`                                                                                                                      |
| `list-item`           | —                      | Generates a principal box + marker box (used by `<li>`)                                                                                       |
| `ruby`                | —                      | Behaves like `<ruby>` (East Asian annotation typography)                                                                                      |
| `ruby-base`           | —                      | Ruby base text box                                                                                                                            |
| `ruby-text`           | —                      | Ruby annotation text box                                                                                                                      |
| `ruby-base-container` | —                      | Anonymous box wrapping ruby bases                                                                                                             |
| `ruby-text-container` | —                      | Behaves like `<rt>` container                                                                                                                 |

Global values also apply: `inherit`, `initial`, `revert`, `revert-layer`, `unset`.

## 5. `position` — Full Enumerated Value List + Containing Block Rules

| Value              | In normal flow?      | Containing block used for offsets                                                                                                                                                                                                                                      |
| ------------------ | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `static` (default) | Yes                  | N/A — top/right/bottom/left/z-index have no effect                                                                                                                                                                                                                     |
| `relative`         | Yes (space reserved) | Offsets calculated relative to its own normal-flow position                                                                                                                                                                                                            |
| `absolute`         | No                   | Nearest ancestor with `position` other than `static` (or nearest ancestor establishing a containing block via `transform`, `filter`, `perspective`, `will-change`, `contain: layout`, etc.) — falls back to the initial containing block (viewport/root) if none found |
| `fixed`            | No                   | Nearest ancestor with `transform`, `filter`, `perspective`, `will-change`, or `contain: paint/layout` set — otherwise the viewport, ignores scrolling                                                                                                                  |
| `sticky`           | Yes                  | Nearest scrolling ancestor + requires at least one of `top`/`right`/`bottom`/`left` to activate                                                                                                                                                                        |

Global values: `inherit`, `initial`, `revert`, `revert-layer`, `unset`.

**Critical mechanic:** setting `transform`, `filter`, `perspective`, or `will-change: transform` on ANY ancestor — even a `static` one — makes that ancestor a containing block for descendant `fixed`/`absolute` elements. This is one of the most common sources of "why did my fixed element stop being fixed" bugs.

## 6. `overflow` — Full Enumerated Value List

```css
overflow: visible; /* default — content spills outside the box, unclipped */
overflow: hidden; /* content clipped, no scrollbars, not scrollable via UI */
overflow: scroll; /* always shows scrollbars, even if content fits */
overflow: auto; /* scrollbars appear only when content overflows */
overflow: clip; /* like hidden, but disallows ALL scrolling, even programmatic */
```

Also settable per-axis: `overflow-x`, `overflow-y`, and logical equivalents `overflow-block`, `overflow-inline`. Shorthand `overflow: <x> <y>` sets both axes independently.

## 7. Stacking Context & `z-index` Mechanics

- `z-index` only has an effect on positioned elements (`position` ≠ `static`) **or** flex/grid items, **or** elements with an explicit stacking-context-creating property.
- Properties that create a new stacking context on their own: `position: fixed`/`sticky`, `position: absolute`/`relative` + `z-index` ≠ `auto`, `opacity` < 1, `transform` ≠ `none`, `filter` ≠ `none`, `will-change` naming a stacking-context property, `mix-blend-mode` ≠ `normal`, `isolation: isolate`, `contain: layout/paint/strict/content`.
- z-index values only compare **within the same stacking context**. A child cannot escape its parent's stacking context, no matter how high its z-index is set.
- Stacking order within a single context (back to front): background/border of the context-forming element → negative z-index children → non-positioned in-flow children → floats → non-positioned inline children → positioned children with `z-index: auto`/`0`, ordered by DOM order → positioned children with explicit positive z-index, low to high.

---

## 8. Margin Collapsing — Full Rules

- Applies **only** to vertical margins of **block-level** elements in **normal flow**.
- Adjacent siblings: `margin-bottom` of one + `margin-top` of the next → collapse to the **larger** of the two (not the sum).
- Parent/first-child: if a parent has no border, padding, inline content, or BFC establishing property between it and its first/last child, the child's margin can collapse through the parent, appearing outside it.
- Empty blocks: an element with no height, border, or padding can collapse its own top and bottom margins into one.
- **Does NOT happen** when: the parent is a flex or grid container, the parent establishes a new Block Formatting Context (`overflow` ≠ `visible`, `display: flow-root`, `float`, `position: absolute/fixed`), or margins belong to elements in different formatting contexts.

## 9. Common Mistakes & Gotchas

- Forgetting `position: relative` on the parent before using `position: absolute` on a child — offsets resolve against the viewport instead.
- Assuming `z-index: 9999` always wins — it loses instantly if it's trapped inside a lower stacking context.
- Using `overflow: hidden` on a scroll container that also needs a `position: sticky` child inside it — sticky silently stops working.
- Forgetting inline elements ignore `width`, `height`, and vertical `margin` entirely.
- Not knowing `visibility: hidden` and `opacity: 0` still reserve layout space, while `display: none` does not.
- Expecting percentage `height` to work on a child when the parent has no explicit height set — it resolves to `auto` and does nothing.
- Applying `box-sizing: border-box` to only some elements, causing inconsistent sizing math across a codebase.

## 10. Best Practices

- Apply a universal `box-sizing: border-box` reset at the top of every project.
- Prefer `flow-root` over legacy clearfix hacks when you need to contain floats or margins.
- Use `flex`/`grid` for layout; reserve `position: absolute` for genuinely overlapping UI (badges, tooltips, modals).
- Explicitly set `position: relative` on any element intended as a positioning anchor — even with no offset values — to document intent.
- Isolate complex UI (modals, dropdowns) with `isolation: isolate` to create a clean, predictable stacking context.
- Use logical properties (`padding-inline`, `margin-block`) for layouts that need to support RTL/LTR languages.

---

## 11. Anti-Patterns

- Chaining ever-increasing `z-index` values (`999`, `9999`, `99999`) instead of diagnosing the actual stacking context.
- Using `position: absolute` for everyday layout instead of flex/grid — brittle, breaks on content/viewport changes.
- Wrapping every layout div in extra markup just to "fix" margin collapsing instead of using `display: flow-root` or flex.
- Setting `overflow: hidden` reflexively to "fix" a layout bug without understanding what it clips.
- Mixing `float`-based layout with modern flex/grid in the same component — legacy pattern with no upside today.

## 12. Comparisons vs Related Concepts

| Concept A            | Concept B            | Key difference                                                                                                          |
| -------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `display: none`      | `visibility: hidden` | none removes from layout entirely; hidden keeps space reserved                                                          |
| `visibility: hidden` | `opacity: 0`         | hidden removes from accessibility tree & click targets; opacity 0 stays clickable/focusable unless handled              |
| `position: absolute` | `position: fixed`    | absolute anchors to nearest positioned ancestor; fixed anchors to viewport (or transformed ancestor)                    |
| `position: sticky`   | `position: fixed`    | sticky respects parent bounds and toggles with scroll; fixed is permanently detached from flow                          |
| `margin`             | `padding`            | margin is outside the border (collapses, transparent); padding is inside the border (never collapses, takes background) |
| `flex`               | `grid`               | flex is one-dimensional and content-driven; grid is two-dimensional and layout-driven                                   |
| `inline-block`       | `flex item`          | inline-block leaves whitespace gaps between elements; flex items don't                                                  |

## 13. Performance Implications

- `position: fixed`/`sticky` elements can trigger their own compositor layer — cheap for scroll performance, but too many layers increases GPU memory pressure.
- Animating `top`/`left`/`right`/`bottom` triggers layout (reflow) on every frame; animating `transform: translate()` instead only triggers composite — dramatically cheaper.
- Deeply nested stacking contexts (many `transform`/`opacity`/`filter` ancestors) increase paint complexity and make browser dev-tools layer analysis harder to reason about.
- `overflow: auto/scroll` containers with large content can create expensive scrollable layers; use `content-visibility: auto` for long off-screen sections where applicable.

---

## 14. Browser / Runtime Support Notes

- `box-sizing: border-box`, all `display` flex/grid values, `position: sticky` — universally supported in all evergreen browsers as of 2026, safe to use without prefixes or fallbacks.
- `display: contents` — supported broadly, but historically had accessibility-tree inconsistencies in some browsers; verify with a screen reader if used on interactive elements.
- `overflow: clip` — supported in all current evergreen browsers; treat as the modern, stricter alternative to `hidden` when you also want to block programmatic scrolling.
- Legacy `display: -webkit-box` (old flexbox syntax) still appears in very old codebases — treat as deprecated, migrate to standard `flex`.

---

## 15. Accessibility Implications

- `display: none` removes an element from the accessibility tree — screen readers skip it entirely; this is correct for truly hidden content.
- `visibility: hidden` also removes it from the accessibility tree and tab order, while `opacity: 0` does **not** — an invisible-but-clickable/focusable element is a common accessibility bug.
- Visual (CSS) reordering via `position`, `flex-direction: row-reverse`, or grid placement does **not** change DOM order — screen readers and keyboard tab order follow the DOM, not the visual layout, so mismatches confuse assistive tech users.
- `display: contents` can strip semantic roles from some elements in certain browser/AT combinations — test before using it on interactive components.
- Sticky/fixed headers can obscure focused elements when navigating by keyboard; account for `scroll-margin-top` on focus targets.

---

## 16. Security Implications

- Absolute/fixed positioning combined with `z-index` and `opacity`/`pointer-events` manipulation is the core mechanism behind **clickjacking** — an invisible positioned element overlaid on a legitimate button to hijack clicks.
- Third-party embedded widgets (ads, iframes) using `position: fixed` with high z-index can visually spoof native UI (fake close buttons, fake system dialogs) — validate third-party embed styling boundaries.
- `overflow: hidden` used to visually "hide" sensitive content is not a security control — the content is still present in the DOM and readable via dev tools or scraping.

## 18. Rapid-Fire Interview One-Liners

- Box model order, inside out: content → padding → border → margin.
- `border-box` makes `width` include padding and border; `content-box` (default) doesn't.
- `inline` elements ignore width, height, and vertical margin.
- `position: absolute` positions relative to the nearest non-static ancestor, or the viewport if none exists.
- `position: fixed` ignores scrolling; `position: sticky` toggles between relative and fixed based on scroll position.
- Sticky breaks silently if any ancestor has `overflow: hidden/auto/scroll`.
- `z-index` only compares within the same stacking context, not globally.
- `opacity < 1`, `transform`, and `filter` all create new stacking contexts.
- Margin collapsing only affects vertical margins of block elements in normal flow — flex/grid containers don't collapse margins.
- `display: none` removes layout space and accessibility presence; `visibility: hidden` removes accessibility presence but keeps space; `opacity: 0` keeps both space and interactivity.

## 19. In React/Next.js Projects

- **Portals & modals:** `createPortal(<Modal />, document.body)` escapes the DOM tree, but not stacking contexts — an ancestor with `transform`/`opacity` for animation (e.g. a Framer Motion wrapper) can still visually trap a "portaled" modal behind other content.
- **CSS Modules / Tailwind resets:** confirm your global stylesheet (or `globals.css` in Next.js App Router) applies `box-sizing: border-box` once at the root — Tailwind's Preflight does this automatically, but hand-rolled CSS Modules setups often forget it.
- **Server-rendered layout shift:** in Next.js, image/media placeholders need explicit width/height or `aspect-ratio` set on the box model to prevent layout shift (CLS) between server-rendered HTML and hydration.
- **Sticky headers inside scrollable dashboards:** a common Next.js layout bug — a `sidebar`/`main` grid with `overflow-y: auto` on the scroll container silently breaks any `position: sticky` element nested inside it.
- **Conditional rendering vs display toggling:** `{condition && <Component />}` removes the element from the DOM entirely (like `display: none` but heavier — full unmount/remount), while toggling a CSS class is cheaper for frequently-toggled UI like tooltips.
- **Client Components with `use client`:** stacking-context bugs from third-party animation libraries (Framer Motion, React Spring) are common in App Router projects because those libraries apply `transform`/`will-change` to wrapper divs by default.

## 20. In the AI Era

- AI assistants reliably generate syntactically correct `position: absolute` rules but frequently **omit the required `position: relative` on the actual parent**, because they can't see your full component/DOM tree context — only the file or snippet in front of them.
- When asked to "fix a z-index issue," AI tools default to **raising the number** rather than diagnosing which stacking context the element is trapped in — this is a pattern-matched "fix," not a reasoned one.
- AI-generated components using animation libraries (Framer Motion, GSAP) often add `transform`/`opacity`/`will-change` to a wrapper without flagging that this silently creates a new stacking context — a dev must manually trace whether that breaks a portal or fixed child elsewhere in the tree.
- AI tools frequently generate `overflow: hidden` as a generic "fix" for visual overflow bugs without checking whether a `position: sticky` descendant depends on that same ancestor **not** clipping/scrolling.
- AI-generated CSS resets sometimes apply `box-sizing: border-box` only to specific selectors instead of universally, reintroducing inconsistent sizing math across a codebase — always check the reset's selector scope.
- **What you must still verify manually:** the actual DOM/component hierarchy (AI can't infer this from a single file), which ancestor is the real containing block, whether a new stacking context was introduced, and whether accessibility properties (`display: none` vs `visibility: hidden` vs `opacity: 0`) match the intended keyboard/screen-reader behavior — none of this is visible from CSS syntax alone, which is exactly why this topic doesn't get automated away.
