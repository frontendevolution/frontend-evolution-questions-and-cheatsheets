# CSS Units Cheatsheet — px, rem, em, vw, %, and everything else (2026)

_The one doc to keep open. Foundations Done Right — HTML & CSS._

---

## 1. Core Definitions & Vocabulary

- **CSS pixel (px):** an absolute, fixed reference unit — not a literal hardware pixel. Browsers scale it against actual device pixels via device-pixel-ratio.
- **Root font-size:** the computed `font-size` of the `<html>` element. Defaults to `16px` in every major browser unless overridden.
- **Em:** relative to the font-size of the element it's applied to (or the nearest ancestor's font-size if the element itself has none set).
- **Rem ("root em"):** relative to the root (`html`) element's font-size only — never affected by nesting.
- **Viewport:** the visible rendering area of the browser window (or device screen). Vw/vh/vmin/vmax/dvh/svh/lvh are all fractions of this.
- **Containing block:** the reference box a percentage or viewport-relative value resolves against — usually the nearest ancestor with a defined value for that property, but the rule differs per property.
- **Absolute unit:** fixed physical/reference size, unaffected by parent, root, or viewport (px, cm, mm, in, pt, pc, Q).
- **Relative unit:** computed relative to something else — parent, root, viewport, or container (em, rem, %, vw, vh, ch, ex, cqw, etc.).

## 2. Full Unit Reference (Exhaustive)

### Absolute length units

| Unit | Meaning                 | Notes                                                   |
| ---- | ----------------------- | ------------------------------------------------------- |
| `px` | CSS reference pixel     | Most common absolute unit on the web                    |
| `pt` | Point (1/72 of an inch) | Print-oriented; rare in web CSS                         |
| `pc` | Pica (12 points)        | Print-oriented; essentially unused in web CSS           |
| `in` | Inch                    | Physical unit; rare, mostly print stylesheets           |
| `cm` | Centimeter              | Physical unit; rare, mostly print stylesheets           |
| `mm` | Millimeter              | Physical unit; rare, mostly print stylesheets           |
| `Q`  | Quarter-millimeter      | Physical unit; almost never used, print-only edge cases |

### Relative length units (font/element-based)

| Unit  | Relative to                                                        | Notes                                                                               |
| ----- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| `em`  | Font-size of the element itself (or nearest ancestor with one set) | Compounds through nesting                                                           |
| `rem` | Font-size of the root `<html>` element                             | Does not compound; global reference                                                 |
| `ex`  | x-height of the element's font                                     | Rarely used; font-metric dependent, inconsistent across fonts                       |
| `ch`  | Width of the "0" character in the element's font                   | Useful for character-based widths (e.g. `max-width: 60ch` for readable line length) |
| `lh`  | Line-height of the element                                         | Newer unit; lets you size things relative to computed line-height                   |

### Viewport-percentage units

| Unit          | Relative to                                | Notes                                                                                                    |
| ------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `vw`          | 1% of viewport width                       | Can include scrollbar width in some browsers, causing overflow                                           |
| `vh`          | 1% of viewport height                      | Classic mobile bug: doesn't shrink when address bar is visible                                           |
| `vmin`        | 1% of the smaller of viewport width/height | Useful for square/consistent scaling elements                                                            |
| `vmax`        | 1% of the larger of viewport width/height  | Less common; used for full-bleed scaling based on dominant axis                                          |
| `dvw` / `dvh` | Dynamic viewport width/height              | Updates live as mobile browser chrome shows/hides — current best practice for full-screen mobile layouts |
| `svw` / `svh` | Smallest possible viewport width/height    | Stable, "worst case" viewport size (chrome fully visible)                                                |
| `lvw` / `lvh` | Largest possible viewport width/height     | Stable, "best case" viewport size (chrome fully hidden)                                                  |

### Container query units (modern, container-relative)

| Unit    | Relative to                       | Notes                                        |
| ------- | --------------------------------- | -------------------------------------------- |
| `cqw`   | 1% of container's width           | Requires `container-type` set on an ancestor |
| `cqh`   | 1% of container's height          | Requires `container-type` set on an ancestor |
| `cqi`   | 1% of container's inline size     | Logical property version of cqw              |
| `cqb`   | 1% of container's block size      | Logical property version of cqh              |
| `cqmin` | 1% of smaller container dimension | Container equivalent of vmin                 |
| `cqmax` | 1% of larger container dimension  | Container equivalent of vmax                 |

### Percentage

| Unit | Relative to                     | Notes                                                                                                                                                                                                               |
| ---- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `%`  | Varies entirely by CSS property | Width % → parent width. Height % → parent's explicit height (or nothing). `padding`/`margin` (top/bottom included) % → parent's **width**, not height. `translate`/`background-position` % → the element's own box. |

## 3. Step-by-Step Resolution Mechanics

1. Browser parses the value and identifies its unit type.
2. For `em`: browser walks up to find the computed `font-size` on the element itself, falling back to the nearest ancestor with one defined.
3. For `rem`: browser reads the computed `font-size` of `<html>` directly — no walking, no nesting math.
4. For `%`: browser looks at the property being set, determines which ancestor property it resolves against (per the CSS spec table for that property), and multiplies.
5. For `vw`/`vh`/`dvh`/etc.: browser reads the current viewport dimensions (accounting for browser chrome if using dynamic variants) and calculates the percentage live, recalculating on resize/scroll.
6. For `cqw`/`cqh`/etc.: browser finds the nearest ancestor with `container-type` set and uses its dimensions instead of the viewport or root.

## 4. Common Mistakes & Gotchas

- Using `px` for font-size, ignoring that it never responds to user browser zoom/accessibility settings.
- Nesting multiple `em`-based font-sizes and being surprised the leaf element is much bigger than intended (compounding).
- Setting `height: 100%` on a child whose parent has no explicit height — it silently resolves to nothing.
- Using `100vh` for a full-screen mobile hero and having it jump or clip when the address bar shows/hides.
- Forgetting that `100vw` can include scrollbar width, causing an unwanted horizontal scrollbar.
- Assuming percentage `padding-top`/`padding-bottom` is relative to the parent's height — it's actually relative to width.
- Mixing `px` and `rem` inconsistently across a design system, causing untraceable "why does this component look different" bugs.
- Forgetting `ch` and `ex` depend on the specific font's metrics, so they render differently across font families.

---

## 5. Best Practices

- Default typography and spacing tokens to `rem` so the entire UI respects user browser zoom/accessibility settings.
- Use `em` intentionally for values that should scale with an element's own local font-size — icon sizing, button padding.
- Reserve `px` for things that must never scale: hairline borders, box-shadow offsets, 1px dividers.
- Prefer `dvh`/`svh` over `vh` for full-screen mobile sections; include `vh` only as a fallback for unsupported browsers.
- Use `clamp()` with `rem` bounds and a `vw` middle value for fluid, accessible responsive typography.
- Use `ch` for setting readable max-width on text blocks (e.g. `max-width: 65ch`).
- Use container query units (`cqw`, `cqi`) when a component's sizing should depend on its container, not the viewport — critical for reusable components.

---

## 6. Anti-Patterns

- Hardcoding every spacing value in `px` "because it's simpler" — breaks accessibility and consistency.
- Using `em` for a design system's global spacing scale — causes uncontrollable compounding across different nesting depths.
- Relying on `100vh` unconditionally for anything full-screen on mobile without testing on a real device.
- Using `%` for height without verifying the entire ancestor chain has explicit heights defined.
- Copy-pasting AI-generated CSS units without checking whether the chosen unit matches actual design intent.

## 7. Comparisons

| Comparison    | Key difference                                                                                                                     |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `rem` vs `em` | Rem = always root-relative, no compounding. Em = locally relative, compounds through nesting.                                      |
| `vh` vs `dvh` | Vh = static viewport height, ignores browser chrome. Dvh = dynamic, updates as chrome shows/hides.                                 |
| `vw` vs `%`   | Vw = relative to the whole viewport. % = relative to the nearest applicable ancestor/container.                                    |
| `px` vs `rem` | Px = fixed, ignores user settings. Rem = scales with user's root font-size preference.                                             |
| `%` vs `cqw`  | % = resolves against parent (varies per property). Cqw = resolves against a defined container, independent of parent chain quirks. |

## 8. Performance Implications

- Unit choice itself has negligible runtime performance cost — this is a layout/accessibility concern, not a rendering-speed one.
- Viewport units (`vw`, `vh`, `dvh`) trigger recalculation on resize and, for dynamic variants, on scroll — excessive use in deeply nested elements can add minor layout-thrash risk during rapid resize events.
- Container query units require the browser to track container size changes, which has a marginally higher computation cost than simple viewport tracking — negligible in practice for typical UI use.

---

## 9. Browser & Runtime Support Notes

- `px`, `em`, `rem`, `%`, `vw`, `vh`, `vmin`, `vmax`: universal support, safe to use anywhere.
- `ch`, `ex`: universal support, but rendering varies slightly by font metrics.
- `dvh`/`svh`/`lvh`/`dvw`/`svw`/`lvw`: supported in all current evergreen browsers (Chrome, Safari, Firefox, Edge) as of 2026 — safe as primary units, but pairing with a `vh` fallback line is still good practice for very old browser support.
- `cqw`/`cqh`/`cqi`/`cqb`/`cqmin`/`cqmax`: supported in all current evergreen browsers, but require `container-type` to be explicitly set on an ancestor or they don't activate.
- `lh` (line-height unit): supported in current evergreen browsers; still relatively niche in production usage.

---

## 10. Accessibility Implications

- `rem`/`em` respect a user's browser-level font-size preference; `px` does not — this is a genuine WCAG-relevant concern, not a style nitpick.
- Low-vision users who increase browser zoom expect proportional scaling across the entire interface; px-locked layouts break that expectation.
- Avoid disabling browser zoom via viewport meta tags — unit choice only helps accessibility if zoom itself is allowed to function.
- Fluid typography with `clamp()` should always keep a sane minimum bound in `rem` so text never becomes unreadably small on any device.

---

## 11. Security Implications

- CSS units themselves carry no direct security risk, but be cautious with user-controllable style values (e.g. dynamic inline styles built from user input) — unvalidated numeric input used in `calc()` or unit strings can be an injection vector if concatenated into raw CSS strings rather than passed through safe style APIs (like React's `style` object or CSS-in-JS with proper escaping).

## 12. Quick Code Reference

```css
html {
  font-size: 16px; /* root reference for all rem calculations */
}

.title {
  font-size: 2rem; /* 32px, scales with root */
  line-height: 1.5; /* unitless multiplier, avoids compounding */
}

.btn {
  font-size: 1rem;
  padding: 0.75em 1.25em; /* scales with the button's own font-size */
}

.hero {
  height: 100vh; /* fallback */
  height: 100dvh; /* preferred: accounts for mobile browser chrome */
}

.readable-text {
  max-width: 65ch; /* readable line length regardless of font-size */
}

.fluid-heading {
  font-size: clamp(1rem, 0.5rem + 2vw, 2.5rem); /* fluid, bounded, accessible */
}
```

## 13. Rapid-Fire Interview One-Liners

- Px = fixed, ignores user zoom. Rem = root-relative, respects user zoom. Em = self/parent-relative, compounds.
- Height percentages need an explicit parent height to resolve against — otherwise they collapse to nothing.
- Vertical padding/margin percentages resolve against the parent's **width**, not height.
- Vh doesn't account for mobile browser chrome; dvh does.
- Ch sizes based on the width of the "0" character — useful for readable line lengths.
- Container query units resolve against a container with `container-type` set, not the viewport or parent chain.
- Rem is the standard default for design system spacing/typography tokens; em is for local, intentional proportional scaling.

## 14. In React/Next.js Projects

- Design system tokens (Tailwind config, CSS variables, styled-components themes) typically define spacing/typography scales in `rem` for consistency and accessibility across the whole app.
- A shared component like `<Card>` or `<Button>` using `padding: 1em` internally creates hidden coupling — its visual size silently shifts depending on the ambient font-size wherever it's rendered (dashboard vs. modal vs. sidebar).
- Tailwind's `h-screen` utility compiles to `height: 100vh` by default — swap to `h-dvh` for mobile-safe full-viewport sections in a Next.js layout.
- CSS Modules and CSS-in-JS solutions inherit the same rem/em/% resolution rules as plain CSS — component scoping doesn't change unit math.
- When building reusable, embeddable components (e.g. a widget dropped into unknown host pages), avoid relying on inherited root font-size — explicitly set a local font-size context instead of trusting `rem`/`em` inheritance from an unknown host.
- Server-rendered Next.js pages don't have access to the client's actual viewport at render time — any critical layout logic dependent on real viewport size still needs to happen client-side or via CSS, not assumed at SSR time.

---

## 15. In the AI Era

- AI assistants frequently default to `height: 100vh` for full-screen sections because it's syntactically common in training data — it looks correct and works on desktop, but breaks on mobile Safari due to browser chrome. Always check for `dvh` usage in generated full-screen layouts.
- AI tools often default font-sizes to `px` out of statistical habit from older training data, silently reintroducing an accessibility regression. A reviewer who doesn't understand the rem/accessibility link will approve this without noticing.
- AI-driven bulk refactors (e.g. an agentic tool converting a legacy codebase from `px` to relative units) can apply `em` uniformly without recognizing compounding risk in nested components — always verify rem was used for anything global, and em only where local scaling was truly intended.
- Automated conversions can also sweep up intentionally-fixed values (hairline borders, shadow offsets) into relative units they were never meant to have — check that these weren't touched.
- AI can write every unit's syntax perfectly, but it has no access to your actual design intent — whether something should respect user zoom, scale with local text, or stay fixed. That judgment call remains the developer's responsibility, in every review, prompt, and merge decision.
