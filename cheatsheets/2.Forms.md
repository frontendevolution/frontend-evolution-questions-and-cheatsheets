# HTML Forms — The Complete Reference (2026)
### Labels, Input Types, Select, Textarea, Attributes & Validation

---

## 1. Core Definitions & Vocabulary

| Term | Definition |
|---|---|
| **Form** | A `<form>` element grouping controls that submit data as a set. |
| **Form control** | Any element that accepts user input: `input`, `select`, `textarea`, `button`. |
| **Label** | Text programmatically associated with a control via `for`/`id` or implicit nesting. |
| **Constraint validation** | The browser's built-in system for checking form values against declared rules (`required`, `pattern`, etc.) before allowing submission. |
| **Controlled component** (React) | An input whose value is driven by React state on every render. |
| **Uncontrolled component** (React) | An input whose value lives in the DOM; React reads it via `ref` only when needed. |
| **Progressive enhancement** | Building a feature (like a form) so it works with plain HTML first, then layering JS on top. |
| **FormData** | A browser API representing form field name/value pairs, usable with or without JS frameworks. |

---

## 2. The `<form>` Element — Full Attribute Surface

```html
<form
  action="/submit"
  method="post"
  enctype="multipart/form-data"
  target="_self"
  autocomplete="on"
  novalidate
  name="signupForm"
>
```

| Attribute | Purpose |
|---|---|
| `action` | URL the form submits to. |
| `method` | `get` (default) or `post`. |
| `enctype` | `application/x-www-form-urlencoded` (default), `multipart/form-data` (needed for file uploads), `text/plain` (rarely used). |
| `target` | Where response loads: `_self`, `_blank`, `_parent`, `_top`. |
| `autocomplete` | `on`/`off` — controls browser autofill for the whole form. |
| `novalidate` | Disables native constraint validation on submit. |
| `name` | Identifies the form (legacy, rarely needed now). |

## 3. Every HTML Input Type (Exhaustive)

| Type | Behavior / Purpose |
|---|---|
| `text` | Default single-line free text. |
| `password` | Masks characters; disables copy in some browsers. |
| `email` | Email keyboard on mobile; basic format validation. |
| `tel` | Numeric/phone keypad on mobile; no format validation. |
| `url` | URL keyboard; validates for URL-like structure. |
| `number` | Numeric spinner UI; value is parsed as a number. |
| `range` | Slider UI between `min` and `max`. |
| `date` | Native date picker; value format `YYYY-MM-DD`. |
| `time` | Native time picker; value format `HH:MM`. |
| `datetime-local` | Combined date + time picker (no timezone). |
| `month` | Month/year picker. |
| `week` | Week/year picker. |
| `search` | Styled as a search field; adds a clear (×) button in most browsers. |
| `tel` | (listed above) |
| `color` | Native color picker; value is a hex string. |
| `checkbox` | Boolean toggle; multiple with same `name` = a set. |
| `radio` | Single choice among a group sharing the same `name`. |
| `file` | File upload; pair with `accept` and `multiple`. |
| `hidden` | Not rendered; submits a fixed value. |
| `submit` | Submits the form. |
| `reset` | Resets form fields to default values. |
| `button` | No default behavior; for JS-driven actions. |
| `image` | Submit button rendered as an image. |

## 4. Global Input Attributes (Exhaustive for Validation/Behavior)

| Attribute | Applies to | Effect |
|---|---|---|
| `required` | most inputs, select, textarea | Blocks submission if empty. |
| `minlength` / `maxlength` | text-like inputs, textarea | Character count bounds. |
| `min` / `max` | number, range, date, time, etc. | Value bounds. |
| `step` | number, range, date, time | Increment granularity. |
| `pattern` | text-like inputs | Regex the value must match. |
| `placeholder` | text-like inputs, textarea | Hint text, not a label. |
| `readonly` | most inputs | Visible, focusable, but not editable; still submits value. |
| `disabled` | all controls | Not interactive; value NOT submitted. |
| `autofocus` | most controls | Focuses element on page load. |
| `autocomplete` | most inputs | Hints browser autofill behavior (`name`, `email`, `new-password`, `off`, etc.). |
| `multiple` | email, file, select | Allows multiple values/files. |
| `accept` | file | Restricts file types (e.g. `image/*`, `.pdf`). |
| `list` | most inputs | Links to a `<datalist>` for suggestions. |
| `inputmode` | text-like inputs | Controls virtual keyboard type without changing value type. |
| `size` | text-like inputs | Visible width in characters. |
| `spellcheck` | text-like inputs, textarea | Enables/disables browser spellcheck. |

## 5. `<label>` — Syntax & Association Methods

**Method 1 — Explicit (preferred):**
```html
<label for="email">Email</label>
<input id="email" name="email" type="email" />
```

**Method 2 — Implicit (nesting):**
```html
<label>
  Email
  <input name="email" type="email" />
</label>
```

**Rules:**
- Explicit association (`for`/`id`) is more robust and works even if you restructure layout with CSS.
- Every form control needs a label — including `<select>` and `<textarea>`.
- `aria-label` or `aria-labelledby` can substitute when a visible label isn't feasible, but should be the exception, not default.
- Never use `placeholder` as your only labeling mechanism.

## 6. `<select>` — Full Syntax

```html
<label for="framework">Framework</label>
<select id="framework" name="framework" multiple size="4" required>
  <optgroup label="Frontend">
    <option value="react" selected>React</option>
    <option value="vue">Vue</option>
  </optgroup>
  <optgroup label="Backend" disabled>
    <option value="node">Node</option>
  </optgroup>
</select>
```

| Element/Attribute | Purpose |
|---|---|
| `<option>` | A single selectable choice. |
| `value` | Value submitted (falls back to text content if omitted). |
| `selected` | Pre-selects the option. |
| `disabled` (on option) | Makes a single choice unselectable. |
| `<optgroup>` | Groups related options with a visual label. |
| `label` (on optgroup) | The group's heading text. |
| `disabled` (on optgroup) | Disables the entire group. |
| `multiple` | Allows selecting more than one option. |
| `size` | Number of visible rows (turns it into a list box). |

## 7. `<textarea>` — Full Syntax

```html
<label for="bio">Bio</label>
<textarea
  id="bio"
  name="bio"
  rows="4"
  cols="50"
  maxlength="500"
  placeholder="Tell us about yourself"
  wrap="soft"
></textarea>
```

| Attribute | Purpose |
|---|---|
| `rows` | Visible height in text lines (NOT a character limit). |
| `cols` | Visible width in characters. |
| `wrap` | `soft` (default, visual wrap only) or `hard` (inserts real line breaks on submit — requires `cols`). |
| `maxlength` / `minlength` | Character bounds. |
| `readonly` / `disabled` | Same semantics as inputs. |

**CSS gotcha:** textareas are user-resizable by default.
```css
textarea { resize: vertical; } /* or none / horizontal / both */
```

## 8. Constraint Validation API (JavaScript)

| Method/Property | What it does |
|---|---|
| `element.checkValidity()` | Returns `true`/`false`; fires `invalid` event if false. |
| `element.reportValidity()` | Same as above, but also shows the browser's native error UI. |
| `element.validity` | A `ValidityState` object (`valueMissing`, `typeMismatch`, `patternMismatch`, `tooLong`, `tooShort`, `rangeUnderflow`, `rangeOverflow`, `stepMismatch`, `badInput`, `customError`, `valid`). |
| `element.validationMessage` | Human-readable browser error string. |
| `element.setCustomValidity(msg)` | Sets a custom validation error; pass `""` to clear it. |
| `form.checkValidity()` | Validates all controls in the form at once. |

**CSS validation hooks:**
```css
input:valid { border-color: green; }
input:invalid { border-color: crimson; }
input:required { }
input:optional { }
input:in-range { }
input:out-of-range { }
input:placeholder-shown { }
```

## 9. Common Mistakes & Gotchas

- Using `placeholder` instead of `label` — fails accessibility and disappears on input.
- Forgetting `type="button"` on non-submit buttons inside a `<form>` — they default to `type="submit"` and trigger unintended submissions.
- Assuming client-side validation is secure — it validates nothing on the server.
- Using `disabled` when you meant `readonly` — disabled fields don't submit their value at all.
- Confusing `rows`/`cols` on textarea with character limits.
- Forgetting `name` attributes — without `name`, a field's value is never submitted.
- Nesting interactive elements (e.g. a button inside a label inside another button) — invalid and behaves unpredictably.
- Relying only on color (`:invalid` red border) to indicate errors — a WCAG failure without text/icon backup.
- Assuming `type="email"`/`type="url"` fully validate real-world correctness — they only check basic format, not deliverability.

## 10. Best Practices

- Always pair a visible `<label>` with every control.
- Choose the most semantically correct `input type` before reaching for custom JS behavior.
- Use native constraint attributes (`required`, `pattern`, `min`, `max`) before writing custom validation logic.
- Group related radio/checkbox sets inside `<fieldset>` with a `<legend>`.
- Always re-validate everything server-side, regardless of client validation.
- Use `autocomplete` attributes correctly (`autocomplete="new-password"` vs `"current-password"`) — this affects password manager behavior.
- Provide clear, text-based error messages, not just color changes.
- Disable submit buttons during pending/async submission to prevent double-submits.

---

## 11. Anti-Patterns

- Building custom dropdowns, checkboxes, or radios from `<div>`s when a native element would work — you re-implement keyboard nav, focus states, and screen reader support for free features you just deleted.
- Validating only in `onChange` handlers with no native attributes as a fallback.
- Using `<div onClick>` as a submit button instead of `<button type="submit">`.
- Blocking paste on password fields (harms password manager usage, doesn't add real security).
- Auto-submitting forms on every keystroke change without debouncing or clear user intent.

---

## 12. Accessibility Implications

- Every control needs an accessible name — via `<label>`, `aria-label`, or `aria-labelledby`.
- `<fieldset>` + `<legend>` are required for radio/checkbox groups so screen readers announce the group purpose.
- Error messages should be linked via `aria-describedby` and ideally announced via `aria-live` regions.
- Required fields should use the `required` attribute (announced by assistive tech) — not just a visual asterisk.
- Focus order should follow visual/logical order; avoid `tabindex` values greater than 0.
- Native form elements come with keyboard support (Tab, Space, Enter, Arrow keys) built in — custom components must reimplement all of it correctly.

---

## 13. Security Implications

- Client-side validation (native or JS) is a UX layer only — it can be bypassed via DevTools or direct API calls.
- Every form input must be re-validated and sanitized server-side.
- `enctype="multipart/form-data"` file uploads must be validated server-side for type, size, and content — never trust the `accept` attribute or client MIME type.
- Autocomplete for sensitive fields (`autocomplete="off"`) doesn't guarantee browsers will honor it — don't rely on it as a security control.
- CSRF protection is unrelated to form validation but must be layered on top of any state-changing form submission.

---

## 14. Performance Implications

- Controlled inputs in React re-render on every keystroke — fine for small forms, can cause jank in very large forms with heavy sibling re-renders.
- Excessive real-time validation (validating on every keystroke across many fields) can cause visible lag in complex forms — debounce where appropriate.
- Native constraint validation runs in the browser engine, not JS — effectively free performance-wise compared to custom JS validation.

---

## 15. Browser/Runtime Support Notes

- All input types listed above are supported in current evergreen browsers (Chrome, Edge, Firefox, Safari).
- `type="date"`, `time`, `datetime-local`, `month`, `week` render differently across browsers (native picker UI varies) — don't assume pixel-identical UI cross-browser.
- `showPicker()` (JS method to programmatically open native pickers) is supported in Chromium and Firefox; check current Safari support before relying on it.
- `:has()` in CSS now enables styling a label based on its input's validity state without JS, supported in all current evergreen browsers.

## 16. In React/Next.js Projects

- **Controlled vs uncontrolled:** Controlled (`value` + `onChange` + state) enables live validation/formatting; uncontrolled (`ref` + `defaultValue`) is lighter for large simple forms.
- **`htmlFor` not `for`:** JSX uses `htmlFor` because `for` is a reserved JS keyword — using `for` silently fails with no error.
- **Native `<form action={serverAction}>` in Next.js:** Modern Next.js (App Router) lets a `<form>`'s `action` point directly at a Server Action, skipping `onSubmit`/`preventDefault`/manual `fetch` — and it works before JS hydrates (progressive enhancement).
- **`useActionState`** returns `[state, formAction, isPending]` — handles pending UI and server-returned validation errors without manual loading booleans.
- **`useFormStatus`** (used inside a child of the form) exposes `pending` for submit button states without prop drilling.
- **Schema validation libraries** (Zod, Valibot) are commonly used inside Server Actions to validate `FormData` server-side — this is the current idiomatic replacement for manually re-implementing checks that `required`/`pattern` already do client-side.
- **Hydration mismatches:** setting `defaultValue` differently between server and client render (e.g. from `Math.random()` or `Date.now()`) causes React hydration warnings on form fields.
- **Don't forget `name` attributes** even in React — `FormData` extraction in Server Actions depends entirely on the `name` attribute, not on React state.

```jsx
// Current idiomatic Next.js form pattern
'use server'
export async function submitForm(prevState, formData) {
  const email = formData.get('email');
  if (!email) return { error: 'Email is required' };
  // persist...
  return { success: true };
}
```
```jsx
const [state, formAction, isPending] = useActionState(submitForm, null);

<form action={formAction}>
  <label htmlFor="email">Email</label>
  <input id="email" name="email" type="email" required />
  {state?.error && <p role="alert">{state.error}</p>}
  <button disabled={isPending}>{isPending ? 'Submitting…' : 'Submit'}</button>
</form>
```

## 17. In the AI Era

**Where AI assistants commonly get this wrong:**
- Generating `<div>`-based "forms" with `onClick` submit handlers instead of a real `<form>` + `<button type="submit">` — breaks Enter-key submission and native validation entirely.
- Using `placeholder` as the only labeling mechanism, skipping `<label>`/`htmlFor` — passes a visual glance, fails accessibility audits.
- Writing `for="..."` instead of `htmlFor="..."` when generating JSX — a silent failure, no console error.
- Producing only client-side validation logic (`if (!email) alert(...)`) with no corresponding server-side re-validation, even when generating a full-stack Next.js feature.
- Defaulting to old patterns — manual `useState` + `onSubmit` + `fetch` — instead of current idiomatic Server Actions + `useActionState`, because training data skews toward older React patterns.
- Marking fields `disabled` when the intent was `readonly` (or vice versa), silently changing whether the value gets submitted.

**What you must manually verify when reviewing AI-generated form code:**
- Is there an actual `<form>` element, or a div pretending to be one?
- Is every input properly labeled (`htmlFor`/`id` match, or implicit nesting)?
- Does client-side validation have a genuine server-side counterpart?
- Is the submit control a real `type="submit"` button inside the form?
- Does the code use current React/Next.js form idioms (Server Actions, `useActionState`) rather than outdated `onSubmit` + manual fetch boilerplate?

**Why this topic doesn't become obsolete just because AI can write the syntax:**
AI can produce form markup instantly, but it cannot judge whether that markup is accessible, secure, or semantically correct — that requires understanding what each tag and attribute is actually for. A form that "looks right" in an AI-generated preview can still fail screen readers, fail keyboard navigation, and accept malicious input, because AI optimizes for visual resemblance to a form, not for meeting the platform contract a form is supposed to fulfill.

## 18. Comparisons vs Related Concepts

| Concept | vs | Key difference |
|---|---|---|
| `label` | `placeholder` | Label = permanent, accessible name. Placeholder = temporary hint, disappears on input. |
| `disabled` | `readonly` | Disabled = not submitted, not focusable. Readonly = submitted, focusable, not editable. |
| Native `<select>` | Custom dropdown component | Native gives free keyboard/mobile/a11y support; custom gives full visual control at the cost of reimplementing that support. |
| Client-side validation | Server-side validation | Client = UX convenience, bypassable. Server = actual security/data integrity boundary. |
| Controlled input (React) | Uncontrolled input (React) | Controlled = React state drives value, re-renders each keystroke. Uncontrolled = DOM holds value, read via ref. |

## 19. Rapid-Fire Interview One-Liners

- **Q: Why use `<label>` instead of just styling text near an input?** A: It creates a programmatic association required for accessibility and click-to-focus behavior.
- **Q: Difference between `disabled` and `readonly`?** A: Disabled fields don't submit their value; readonly fields do.
- **Q: Is client-side validation sufficient for security?** A: No — it must always be paired with server-side validation.
- **Q: What does `inputmode` do that `type` doesn't?** A: Changes the virtual keyboard shown without changing how the value is parsed or validated.
- **Q: Why is `for` written as `htmlFor` in JSX?** A: Because `for` is a reserved word in JavaScript.
- **Q: What does `enctype="multipart/form-data"` enable?** A: File uploads within form submission.
- **Q: What's the current idiomatic way to handle forms in Next.js App Router?** A: Native `<form action={serverAction}>` combined with `useActionState` and `useFormStatus`.
- **Q: What does `reportValidity()` do differently from `checkValidity()`?** A: It also triggers the browser's visible native error UI.
- **Q: Why should `<fieldset>`/`<legend>` wrap radio groups?** A: So assistive tech announces the group's purpose, not just individual options.
- **Q: What happens to a form field's value if the `name` attribute is missing?** A: It is never included in the submitted data.
