# CSS Custom Properties & Theming — The Complete Reference

*Foundations Done Right · HTML & CSS · Advanced*

---

## 1. Core Definitions & Vocabulary

- **Custom property**: an author-defined CSS property, prefixed `--`, that stores a value to be reused via `var()`. Officially "CSS Custom Properties for Cascading Variables."
- **CSS variable**: informal name for the same thing — the spec calls them custom properties, `var()` is the *function* that reads them.
- **Custom property vs preprocessor variable**: preprocessor variables (Sass `$x`) are compile-time text substitution; custom properties are live, runtime, cascade-aware values in the DOM.
- **`var()`**: the function used to substitute a custom property's value into a regular property.
- **Fallback value**: the second argument to `var()`, used if the custom property is unset or invalid.
- **Registered custom property**: one declared via `@property`, giving it a type, initial value, and inheritance behavior — unlocks animation and stricter validation.
- **Unregistered custom property**: the default — untyped, treated as a raw token stream until substituted, always inherits, no default/initial value unless you set one.
- **Substitution value**: the raw, unparsed token sequence a custom property holds until it's consumed by `var()` in an actual property — this is why invalid custom property *values* don't invalidate the whole declaration until use.
- **Design token**: a named, reusable design decision (color, spacing, radius) — custom properties are the runtime implementation mechanism for design tokens in CSS.
- **Theming**: swapping a coherent set of custom property values (a "theme") at a scope, typically via a class, attribute, or media query, without touching component CSS.

## 2. Full Syntax & API Surface

```css
/* Declaration */
--brand-color: #6c5ce7;
--spacing-unit: 8px;
--font-stack: "Inter", system-ui, sans-serif;
--empty-but-valid: ; /* valid: empty value */

/* Consumption */
.button {
  color: var(--brand-color);
  padding: var(--spacing-unit);
}

/* With fallback */
.button {
  color: var(--brand-color, blue);
}

/* Nested fallback chain */
.button {
  color: var(--user-color, var(--brand-color, black));
}

/* Fallback with multiple comma-containing values (shorthand) */
.grid {
  grid-template-columns: var(--cols, 1fr, 1fr, 1fr);
}

/* Custom property in a custom property (composition) */
--gap: 8px;
--gap-2x: calc(var(--gap) * 2);

/* Registered custom property */
@property --angle {
  syntax: "<angle>";
  inherits: false;
  initial-value: 0deg;
}

/* Scoped to :root (global) */
:root {
  --page-bg: white;
}

/* Scoped to a component */
.card {
  --card-padding: 16px;
  padding: var(--card-padding);
}

/* @scope for donut/limited scoping (modern) */
@scope (.card) to (.card__nested-widget) {
  :scope { --card-padding: 24px; }
}
```

**Key syntax rules:**
- Custom property names are **case-sensitive**: `--Color` ≠ `--color`.
- Any valid identifier after `--` works, including `--123abc`, `--data-value` — but avoid starting with digits for readability.
- Values can be *any* token sequence — not validated until substituted (this is unique among CSS properties).
- `var()` takes exactly **one** custom property name + optional fallback (fallback can itself contain commas, e.g. inside `var(--x, 1px, 2px)` — everything after the first comma is the fallback).
- You cannot use `var()` in a **property name**, **selector**, or **media query feature name** (except via newer `env()`/container query workarounds) — only in *value* positions.

## 3. `@property` — Registered Custom Properties (CSS Houdini)

```css
@property --highlight-opacity {
  syntax: "<number>";
  inherits: false;
  initial-value: 1;
}
```

- **`syntax`** (required): a typed grammar string — `"<color>"`, `"<length>"`, `"<percentage>"`, `"<number>"`, `"<integer>"`, `"<angle>"`, `"<time>"`, `"<resolution>"`, `"<url>"`, `"<image>"`, `"<custom-ident>"`, `"<transform-function>"`, `"*"` (any token, default for unregistered).
- **`inherits`** (required): `true`/`false` — explicit, unlike unregistered properties which always inherit.
- **`initial-value`** (required unless `syntax: "*"`): the fallback used at the root and whenever the value is invalid at computed-value time.
- **Why it matters**: unlocks **smooth animation/transition** of custom properties (browsers can't interpolate an untyped token stream — `10px` → `20px` needs a known type to tween), enables **type-checking** (invalid values fall back instead of silently breaking), and improves **paint performance** in some engines since the browser knows it doesn't need to re-parse.
- JS equivalent: `CSS.registerProperty({...})` — same capability, imperative API.
- Also declarable via JS: `CSS.registerProperty()`.

## 4. Cascade, Scoping & Inheritance — Step by Step

1. **Declaration parses successfully almost always** — because the value is an unparsed token stream, `--x: literally anything;` is syntactically valid CSS (barring basic tokenization errors).
2. **Custom properties participate in the cascade** like any property: specificity, source order, `!important`, layers (`@layer`) all apply to *which declaration wins* for a given `--name` on a given element.
3. **Inheritance**: unregistered custom properties **always inherit** (like `color`), regardless of the property they'll eventually feed. Registered ones inherit per `@property`'s `inherits` flag.
4. **Resolution happens at computed-value time, per element** — a custom property doesn't have "a value," it has a value *at a given element in the tree*, since it's re-resolved through cascade + inheritance for every element.
5. **`var()` substitution happens when the property using it is computed** — not at parse time. If `--x` is invalid at that point, the *whole declaration* (e.g. `color: var(--x)`) becomes invalid and falls back to its fallback value or the property's inherited/initial value — this is called **"invalid at computed-value time" (IACVT)**.
6. **No fallback + invalid = the property using `var()` resets to its inherited or initial value**, not "nothing happens" — a very common misconception.
7. **Cyclic references** (`--a: var(--b); --b: var(--a);`) resolve to the **guaranteed-invalid value** for all properties in the cycle.
8. **`@scope`** creates limited-scope cascades — donut scoping (`@scope (.card) to (.card__widget)`) lets you theme a region while excluding a nested subregion.

---

## 5. Fallback Value Mechanics

- `var(--x, fallback)` uses `fallback` **only if `--x` is unset (not declared/inherited) or invalid at computed-value time** — not if it's merely falsy or empty string.
- An explicitly set `--x: ;` (empty) is a **valid, set value** (empty token stream) — the fallback will **not** trigger.
- Fallbacks can reference other custom properties, chain arbitrarily deep, and contain full value lists with commas.
- Fallback is **not** the same as `initial-value` from `@property` — fallback is a per-use-site default; `initial-value` is a per-property default at the property level.

## 6. Theming Architecture Patterns

- **Two-tier token system**: global "primitive" tokens (`--color-purple-500: #6c5ce7`) feeding semantic tokens (`--color-brand: var(--color-purple-500)`) — components only ever consume semantic tokens.
- **Class-based theme switch**: `.theme-dark { --bg: #111; --fg: #eee; }` toggled on `<html>`/`<body>` via JS.
- **Attribute-based theme switch**: `[data-theme="dark"] { --bg: #111; }` — more explicit, avoids class-name collisions, easy to combine with `prefers-color-scheme` default.
- **`light-dark()` function (modern, widely supported 2024+)**: `color: light-dark(white, black);` combined with `color-scheme: light dark;` — lets the *browser* pick per user/system preference without duplicating rules.
- **Media-query-driven theming**: `@media (prefers-color-scheme: dark) { :root { --bg: #111; } }` — respects OS-level preference automatically.
- **`prefers-contrast` / `prefers-reduced-motion` theming**: same custom-property-swap pattern extends to accessibility preferences, not just light/dark.
- **Component-scoped overrides**: a component declares sane defaults (`--button-bg: var(--color-brand, blue)`) so it works standalone, but any ancestor can override `--button-bg` to retheme without editing component CSS.
- **Runtime theming via JS**: `element.style.setProperty('--brand-color', userColor)` — the single biggest practical advantage over Sass variables, since Sass variables don't exist at runtime.
- **Container/scoped themes**: multiple themes coexisting on one page (e.g. a CMS admin with theme-preview panes) by scoping variables to a container rather than only `:root`.

## 7. Common Mistakes & Gotchas

- Forgetting **unregistered custom properties can't be animated/transitioned** smoothly — the browser treats the value as a discrete token swap, not an interpolatable number, unless registered via `@property`.
- Assuming `var(--undefined-var)` with no fallback silently "does nothing" — it actually invalidates the declaration back to initial/inherited value.
- Confusing **`:root`** with **`html`** — they're usually equivalent in specificity terms for this use case, but `:root` has higher specificity (a pseudo-class) than the type selector `html`, which matters in rare conflicts.
- Setting custom properties inside `@media` queries expecting them to *only* apply there, forgetting they still cascade/inherit normally — no special "media scoping" magic beyond normal cascade rules.
- Using custom properties for **values needed in selectors or media features** (e.g. breakpoints) — this doesn't work; `var()` isn't valid in most selector/media contexts.
- Overusing `!important` on custom property declarations to "win" theming conflicts instead of fixing specificity/source order.
- Not accounting for the **empty-value gotcha**: `--x: ;` is valid and will NOT trigger `var()`'s fallback, unlike `--x: initial;` which *does* make it invalid/unset for fallback purposes at that scope.
- Forgetting custom properties defined on `*` or overly broad selectors can create expensive inheritance recomputation across large trees.
- Deeply nested `var(--a, var(--b, var(--c, var(--d, ...))))` fallback chains that become unreadable and hard to debug.
- Naming collisions between unrelated components using generic names like `--color` or `--size` at global scope.

## 8. Best Practices

- Namespace tokens by domain: `--color-*`, `--space-*`, `--font-*`, `--radius-*`, `--shadow-*`.
- Build a **two-layer token architecture** (primitive → semantic) so theme swaps only touch semantic tokens.
- Always give component-level custom properties **sane fallbacks** so components degrade gracefully in isolation (e.g. in Storybook, or copy-pasted elsewhere).
- Use `@property` for anything you intend to animate/transition, or want strict type safety on.
- Prefer `light-dark()` + `color-scheme` for simple light/dark cases; reserve manual class/attribute theming for multi-brand or >2-theme systems.
- Document your token contract (which `--*` names a component reads) as its public theming API — treat it like prop types.
- Co-locate component-default custom properties with the component's own selector, not buried in a distant global sheet.
- Use `@scope` for "donut" theming needs instead of fighting specificity with extra classes.

---

## 9. Anti-Patterns

- Using custom properties as a replacement for **all** Sass functionality (math, loops, mixins) — they don't do computation or logic; pair with `calc()` but don't expect Sass-style programmability.
- One giant flat `:root` block with hundreds of ungrouped, unnamespaced variables — impossible to reason about ownership or override safely.
- Reimplementing a full design-token pipeline by hand in raw CSS when a tool (e.g. Style Dictionary) generating custom properties from a single source of truth would prevent drift.
- Using JS to rewrite entire stylesheets for theming when swapping a handful of custom properties would suffice — needlessly expensive.
- Putting **structural** layout values (that need calculation logic across breakpoints) into custom properties expecting CSS to "figure it out" — still needs `clamp()`/`calc()`/container queries doing real work.

## 10. Custom Properties vs Related Concepts (Comparison)

| | Custom Properties (`--x`) | Sass/LESS Variables (`$x`) | Inline `style` attr |
|---|---|---|---|
| Resolved | Runtime, per-element | Compile-time, text substitution | Runtime |
| Cascade-aware | Yes | No (just text swap) | Highest specificity, no cascade participation from stylesheet |
| Inheritable | Yes (unregistered) | No concept of inheritance | No |
| JS-readable/writable | Yes, via `getComputedStyle`/`setProperty` | No (gone after build) | Yes, but per-element only |
| Animatable | Only if registered via `@property` | N/A | Yes (it's just a style) |
| Media-query reactive | Yes, naturally | Requires recompilation | No |
| Typed/validated | Optional, via `@property` | Loosely, at build time | No |

## 11. Performance Implications

- Custom properties add **cascade/inheritance recomputation cost** — deeply nested trees with many inherited custom properties changed frequently (e.g. on `:root` during animation) can trigger wide recalculation.
- Changing a custom property that many descendants consume via `var()` can cause **style recalculation across the whole subtree**, similar to changing `color`.
- Registered properties (`@property`) with `inherits: false` can reduce recalculation scope since the browser knows it's not inherited.
- Animating an unregistered custom property doesn't actually animate smoothly — browsers may reject the transition entirely or jump discretely, wasting the transition timing setup for nothing.
- Custom properties used purely for **static** theming (set once, rarely changed) have negligible runtime cost — the perf conversation matters mainly for **frequently mutated** ones (e.g. JS-driven per-frame updates for animation/gestures).
- Prefer `@property`-registered numeric/length values for JS-driven per-frame custom property updates (e.g. drag interactions) since the browser can optimize typed values better than raw token streams.

## 12. Browser / Runtime Support Notes

- Basic custom properties + `var()`: supported in **all modern evergreen browsers** for years — a safe baseline with zero polyfill need in any current 2026 target matrix.
- `@property` (registered custom properties): supported across current Chromium, Firefox, and Safari — safe to use in 2026 for progressive enhancement (unsupported browsers just treat the value as unregistered, no hard failure).
- `light-dark()`: supported across current major browser versions — safe as a primary theming mechanism in 2026 projects, but confirm your project's minimum supported browser floor if targeting older enterprise/embedded browsers.
- `@scope`: newer than the above; check your specific browser support floor before relying on it as the *only* scoping mechanism — have a class-based fallback path for critical theming if targeting older browser versions.
- No polyfill can fully replicate `@property`'s animation capabilities — if you must support a browser lacking it, the fallback is JS-driven animation (rAF + inline styles) instead of CSS transitions.

## 13. Accessibility Implications

- Theming via custom properties is the standard mechanism for implementing **`prefers-color-scheme`** and **`prefers-contrast`** support — a core accessibility requirement, not an aesthetic nicety.
- Respecting `prefers-reduced-motion` often means swapping `--transition-duration`/`--animation-duration` custom properties to `0s` rather than removing animation code entirely — keeps one code path.
- High-contrast/forced-colors mode (`forced-colors: active`) can override custom-property-driven colors entirely at the OS level — test theming under Windows High Contrast Mode / `forced-colors`, since your custom-property values may be ignored in favor of system colors.
- Ensure themed color pairs (background/foreground custom properties) maintain **sufficient contrast ratio** in every theme variant you ship — a token system makes it easy to accidentally ship a dark-mode pair that fails WCAG contrast because it wasn't manually re-audited.
- Don't rely solely on `color-scheme` metadata to fix native form control contrast — verify manually, especially for custom `<select>`/`<input>` styling layered on top.

---

## 14. Security Implications

- Custom properties are **not** an injection vector by themselves, but concatenating **untrusted user input directly into a custom property value** via `style="--user-color: ${input}"` without sanitization can enable CSS injection (e.g. `expression()`-style legacy attacks are dead, but `url()`-based data exfiltration via CSS `background-image` reading a maliciously injected custom property is a real, documented technique).
- If accepting user-driven theme values (e.g. a "brand color" the user types in), validate the input is a legitimate color/length token **before** injecting it as a custom property value — don't trust raw string concatenation into `<style>` or inline `style` attributes.
- `url()` values inside custom properties (e.g. `--bg-image: url(...)`) can be exploited for tracking-pixel-style requests if user input is allowed to control them unsanitized — same risk class as any user-controlled URL.

## 15. Quick Code Example

```css
/* Token layer */
:root {
  color-scheme: light dark;
  --color-brand-500: #6c5ce7;
  --color-bg: light-dark(#ffffff, #0f0f10);
  --color-fg: light-dark(#111111, #f5f5f5);
  --space-2: 8px;
  --radius-md: 8px;
}

@property --angle {
  syntax: "<angle>";
  inherits: false;
  initial-value: 0deg;
}

.card {
  --card-padding: var(--space-2);
  background: var(--color-bg);
  color: var(--color-fg);
  padding: var(--card-padding);
  border-radius: var(--radius-md);
  background-image: conic-gradient(from var(--angle), #6c5ce7, #00cec9);
  transition: --angle 0.6s ease; /* only works because --angle is registered */
}

.card:hover {
  --angle: 360deg;
}
```

## 17. In React/Next.js Projects

- **CSS Modules + custom properties**: define theme tokens in a global stylesheet (`globals.css` in the App Router) and consume via `var()` inside scoped `.module.css` files — avoids prop-drilling styles through components.
- **Theme switching without hydration mismatches**: setting `data-theme` on `<html>` based on user preference must avoid a flash-of-wrong-theme/hydration mismatch in Next.js SSR — commonly solved with a small inline `<script>` in `app/layout.tsx`'s `<head>` that runs before paint and sets the attribute from `localStorage`/`prefers-color-scheme`, since React can't safely read `window` during server render.
- **CSS-in-JS libraries** (e.g. vanilla-extract, styled-components) increasingly compile *to* native custom properties rather than runtime style injection — check whether your styling library's "theme" object is emitting `--*` properties under the hood, which changes how you debug it in DevTools.
- **Tailwind + custom properties**: Tailwind v4's theming model is built on CSS custom properties directly (`@theme` in your CSS, generating `--color-*`/`--spacing-*` variables) — arbitrary values like `bg-[--brand-color]` read custom properties straight from the cascade.
- **Component libraries (shadcn/ui, Radix-based systems)**: theming is done almost entirely via overriding a documented set of `--*` custom properties at `:root` or a wrapper element, not by editing component source — know the token contract before customizing.
- **Server Components can't use `useState`/JS-driven theme toggles** — interactive theme switches must live in a Client Component (`"use client"`), while the static token *definitions* stay in global CSS shipped from the server.
- **Per-instance theming via inline style props**: `<Card style={{ '--card-padding': '24px' } as React.CSSProperties}>` is a common React pattern for one-off overrides — note the TypeScript cast needed since custom properties aren't in the default `CSSProperties` type.
- **CSS Modules scoping doesn't scope custom properties** — a `--card-padding` declared in one module is still globally cascading/inheriting like any custom property; only the *class name* is hashed/scoped, not custom property names, so namespacing collisions are still your responsibility.
- **Next.js `next/font`** exposes font variables (e.g. `variable: '--font-inter'`) specifically as CSS custom properties you apply to a wrapper `className`, integrating directly with this whole system.

## 18. In the AI Era

- **AI assistants frequently generate `var()` calls without fallbacks**, especially in scaffolded component libraries — silently breaks the whole declaration if the token isn't defined yet in that context; you must manually verify every generated `var(--x)` either has a sane fallback or guaranteed upstream definition.
- **AI-generated "dark mode" code often duplicates entire rule sets** (`.dark .card { ... }` mirroring `.card { ... }`) instead of just swapping custom property values — a strong signal the model defaulted to a pre-token-era pattern; push it to only redefine the `--*` values per theme.
- **AI tools commonly forget `@property`'s `inherits` and `initial-value` are required fields** (unless `syntax: "*"`) and generate incomplete `@property` blocks that silently fail to register — you must manually confirm all three fields are present and check DevTools' Computed panel to confirm the property actually registered.
- **AI assistants often propose transitioning/animating a raw custom property** without registering it via `@property` first — looks correct in the diff, does nothing at runtime; this is one of the most common "looks right, silently no-ops" bugs to catch in review.
- **AI-generated theming code sometimes hardcodes color values redundantly alongside custom properties** ("defensive" duplication) instead of trusting the token — defeats the entire purpose of a theming layer and creates drift; flag any hex/rgb literal sitting next to a `var()` call in the same declaration.
- **AI tools frequently confuse Sass variable syntax and CSS custom property syntax** in mixed codebases (`$brand-color` vs `--brand-color`), especially when migrating or refactoring — always confirm the generated code matches your actual build pipeline's variable system.
- **Why this doesn't become obsolete**: AI can write syntactically valid custom-property declarations all day, but it doesn't inherently reason about *cascade timing*, *invalid-at-computed-value-time* fallback behavior, or *inheritance scope* — these require understanding the runtime resolution model, which is exactly where subtle, hard-to-spot bugs (wrong theme flashing, silently un-animated properties, broken fallback chains) get shipped without a human who understands the mechanics catching them in review.
